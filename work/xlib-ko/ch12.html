12장. 입력 장치 함수 (Input Device Functions)

이 장은 키보드와 포인터(보통 마우스)를 프로그램이 직접 다루는 함수들을 설명한다. 다루는 내용은 다음과 같다.

  • 포인터 전체 또는 특정 버튼을 grab(독점)하기
  • 키보드 전체 또는 특정 키를 grab하기
  • 멈춰 둔(frozen) 이벤트 처리를 다시 진행시키기
  • 포인터를 프로그램으로 옮기기
  • 입력 포커스 정하기
  • 키보드·포인터 설정(벨, 자동 반복, 가속 등) 바꾸기
  • 키보드 인코딩(KeyCode와 KeySym의 대응, modifier 매핑) 다루기

12.1 포인터 grab (Pointer Grabbing)

grab이 왜 필요한가

보통 X 서버는 키보드나 마우스 이벤트가 생기면 곧바로 "알맞은" 클라이언트에게 보낸다. 누가 알맞은지는 포인터가 놓인 창과 입력 포커스로 정해진다. 그런데 이것만으로는 부족한 경우가 있다. 예를 들어 마우스 버튼을 누른 채 끌어서 영역을 고르는 동안 포인터가 내 창 밖으로 나가면, 그다음 움직임과 버튼 놓기(ButtonRelease) 이벤트는 다른 창으로 가 버린다. 메뉴를 띄우는 동안 사용자가 너무 빨리 버튼을 놓으면, 놓기 이벤트가 메뉴 창이 생기기 전에 처리되어 엉뚱한 곳으로 갈 수도 있다.

grab은 이런 문제를 풀기 위한 장치다. 버튼이나 키가 grab되면, 그 이벤트는 원래 받을 클라이언트 대신 grab한 클라이언트에게 간다. 포인터와 키보드는 따로따로 제어할 수 있다.

동기(sync) 모드와 비동기(async) 모드

  • 비동기 모드(GrabModeAsync): grab 중에도 서버는 이벤트를 평소처럼 계속 처리한다.
  • 동기 모드(GrabModeSync): grab한 클라이언트가 허락할 때까지(XAllowEvents) 서버가 그 장치의 이벤트를 더 처리하지 않는다. 이 상태를 장치가 "얼었다(frozen)"고 한다. 실제 키 입력이나 마우스 움직임은 버려지지 않고 서버 안에 쌓여 있다가 나중에 처리된다. grab을 일으킨 이벤트를 다시 처리하게(replay) 할 수도 있다.

장치가 얼어 있으면, 클라이언트가 보는 장치의 "논리적 상태"는 실제 물리적 상태보다 늦을 수 있다. 예를 들어 사용자는 이미 버튼을 놓았어도, 쌓인 이벤트가 처리되기 전까지 서버는 버튼이 눌린 것으로 본다.

능동 grab과 수동 grab

  • 능동(active) grab: 클라이언트가 XGrabPointer, XGrabKeyboard를 호출해 지금 바로 장치를 독점한다.
  • 수동(passive) grab: "이 창에서 이 버튼(또는 키)이 눌리면 그때 grab해 달라"고 미리 등록해 둔다(XGrabButton, XGrabKey). 실제로 눌리는 순간 능동 grab으로 바뀐다.

수동 grab은 믿을 수 있는 팝업 메뉴를 만들 때 편하다. 버튼을 동기 모드로 수동 grab해 두면, 버튼 누르기(down) 이벤트가 grab을 일으키면서 포인터 이벤트 처리를 얼린다. 그동안 팝업 창을 화면에 띄우고(map) 나서 이벤트 처리를 다시 허락하면, 이어지는 버튼 놓기(up) 이벤트는 팝업 창을 기준으로 올바르게 처리된다.

타임스탬프와 CurrentTime

이 장의 많은 함수가 time 인자를 받는다. 이유는 이렇다. 서버는 입력 포커스가 마지막으로 바뀐 시각, 키보드·포인터가 마지막으로 grab된 시각, selection이 마지막으로 바뀐 시각을 기억한다. 내 프로그램이 이벤트에 늦게 반응하는 사이에 다른 프로그램이 이미 포인터를 가져갔을 수도 있다. 이때 요청에 "내가 반응하는 그 이벤트의 시각"을 넣어 보내면, 그 뒤에 누군가 다른 조작을 했을 경우 내 요청은 효과가 없게 된다. 즉 늦게 도착한 옛 요청이 새 상태를 덮어쓰지 못하게 막는 장치다.

  • 타임스탬프는 밀리초 단위이고, 보통 서버가 마지막으로 리셋된 뒤부터 센 값이다. 약 49.7일마다 한 바퀴 돌아 0으로 돌아간다.
  • 서버는 현재 시각 T를 기준으로 타임스탬프 공간의 절반을 T보다 "나중"으로 본다. 그래서 값이 한 바퀴 돌아도 앞뒤 비교가 된다.
  • CurrentTime은 서버가 절대 만들지 않는 특별한 값으로, 요청에서 "지금 서버 시각"을 뜻한다.
가능하면 CurrentTime 대신 지금 처리 중인 이벤트의 time 필드(예: ev.xbutton.time)를 넘긴다. 그래야 위에서 말한 경쟁 상황에서 안전하다. CurrentTime은 이벤트와 상관없이 grab할 때나 간단한 테스트용으로 쓴다.

마스크 비트

포인터 grab 함수에 넘기는 event_mask에 쓸 수 있는 비트는 ButtonPressMask, ButtonReleaseMask, EnterWindowMask, LeaveWindowMask, PointerMotionMask, PointerMotionHintMask, Button1MotionMask~Button5MotionMask, ButtonMotionMask, KeymapStateMask이다. 수동 grab의 modifiers에 쓰는 keymask 비트는 ShiftMask, LockMask, ControlMask, Mod1Mask~Mod5Mask이다.

XGrabPointer

int XGrabPointer(Display *display, Window grab_window, Bool owner_events,
                 unsigned int event_mask, int pointer_mode, int keyboard_mode,
                 Window confine_to, Cursor cursor, Time time);

포인터를 지금 바로 능동 grab한다. 성공하면 GrabSuccess를 돌려준다. 이후 포인터 이벤트는 grab한 클라이언트에게만 간다. 같은 클라이언트가 이미 grab 중이면 새 grab으로 덮어쓴다.

  • owner_events: False면 모든 포인터 이벤트가 grab_window 기준으로 보고되고, event_mask에 고른 것만 온다. True면, 원래 이 클라이언트의 어떤 창으로 갈 이벤트는 평소처럼 그 창으로 보고되고, 그렇지 않은 이벤트만 grab_window 기준으로(event_mask에 있으면) 보고된다. 어느 쪽이든 보고되지 않은 이벤트는 버려진다.
  • pointer_mode / keyboard_mode: GrabModeAsync 또는 GrabModeSync. Sync면 그 장치가 얼고, XAllowEvents를 부르거나 grab이 풀릴 때까지 이벤트가 생기지 않는다. pointer_mode가 Async이고 이 클라이언트가 포인터를 얼려 둔 상태였다면 얼림이 풀린다.
  • confine_to: 포인터를 이 창 안에 가둔다(None이면 가두지 않음). grab_window와 아무 관계없는 창이어도 된다. 포인터가 처음에 그 창 밖에 있으면 grab 직전에 가장 가까운 가장자리로 자동 이동(warp)되고, 그 창이 나중에 움직이거나 크기가 바뀌어도 포인터가 안에 남도록 자동으로 옮겨진다.
  • cursor: grab 중 어디에 있든 보여 줄 커서. None이면 포인터가 grab_window나 그 하위 창 안에 있을 때는 그 창의 보통 커서를, 밖에 있을 때는 grab_window의 커서를 보여 준다.
  • time: 타임스탬프 또는 CurrentTime.

실패하면 다음 값을 돌려준다.

반환값뜻
GrabNotViewablegrab_window나 confine_to 창이 보이지 않는 상태(viewable 아님)이거나, confine_to가 루트 창 밖에 완전히 벗어나 있음
AlreadyGrabbed다른 클라이언트가 이미 포인터를 능동 grab 중
GrabFrozen다른 클라이언트의 능동 grab 때문에 포인터가 얼어 있음
GrabInvalidTimetime이 마지막 포인터 grab 시각보다 이르거나 현재 서버 시각보다 늦음

성공하면 마지막 포인터 grab 시각이 time으로 바뀐다(CurrentTime이면 현재 서버 시각). EnterNotify/LeaveNotify 이벤트가 생기며, BadCursor, BadValue, BadWindow 오류가 날 수 있다.

원문은 time 인자가 필요한 예를 하나 든다. 둘 다 클릭하면 포인터를 grab하는 두 프로그램이 있을 때, 둘 다 이벤트의 타임스탬프를 넘기면 두 번째 프로그램이 더 빨리 깨어나 먼저 grab에 성공할 수 있다. 그러면 첫 번째 프로그램은 자기 요청이 처리되기 전에 다른 프로그램이 grab했다는 결과(실패 반환값)를 받는다.

함정: 반환값을 꼭 확인한다. 창이 아직 map되지 않았거나(MapNotify 전) 다른 프로그램(창 관리자, 화면 잠금 등)이 grab 중이면 실패한다. 실패했는데 grab된 줄 알고 동작하면 이벤트가 오지 않아 프로그램이 멈춘 것처럼 보인다.

XUngrabPointer

XUngrabPointer(Display *display, Time time);

이 클라이언트가 XGrabPointer나 XGrabButton, 또는 평범한 버튼 누르기로 얻은 능동 grab을 풀고, 쌓여 있던 이벤트도 풀어 준다. time이 마지막 grab 시각보다 이르거나 현재 서버 시각보다 늦으면 풀지 않는다. EnterNotify/LeaveNotify가 생긴다.

서버는 다음 경우에 자동으로 포인터 grab을 푼다: 능동 grab의 이벤트 창이나 confine_to 창이 보이지 않게 될 때, 또는 창 재배치 때문에 confine_to 창이 루트 창 밖으로 완전히 벗어날 때.

"평범한 버튼 누르기"도 grab이다. X에서는 버튼을 누르면 그 버튼을 받은 클라이언트가 버튼을 모두 놓을 때까지 자동으로 포인터를 잡는다(implicit grab). 그래서 끌기 동작만 할 때는 굳이 XGrabPointer를 부르지 않아도 ButtonRelease가 내 창으로 온다. 다만 커서를 바꾸거나 포인터를 가두거나 받을 이벤트를 바꾸려면 명시적으로 grab한다.

XChangeActivePointerGrab

XChangeActivePointerGrab(Display *display, unsigned int event_mask,
                         Cursor cursor, Time time);

이미 능동 grab 중일 때 event_mask와 커서만 바꾼다. time 조건은 XUngrabPointer와 같다. XGrabButton으로 등록한 수동 grab의 설정에는 영향을 주지 않는다. 예를 들어 끌기 도중 Shift를 누르면 커서 모양을 바꾸는 데 쓸 수 있다. BadCursor, BadValue 오류가 날 수 있다.

XGrabButton / XUngrabButton

XGrabButton(Display *display, unsigned int button, unsigned int modifiers,
            Window grab_window, Bool owner_events, unsigned int event_mask,
            int pointer_mode, int keyboard_mode, Window confine_to, Cursor cursor);

XUngrabButton(Display *display, unsigned int button, unsigned int modifiers,
              Window grab_window);

XGrabButton은 수동 grab을 등록한다. 앞으로 다음 조건이 모두 맞으면 포인터가 (XGrabPointer처럼) 능동 grab되고, 마지막 grab 시각은 버튼이 눌린 시각으로 정해지며, 그 ButtonPress 이벤트가 보고된다.

  • 포인터가 grab되어 있지 않고, 지정한 modifier 키들이 눌린 상태에서 지정한 버튼이 눌렸으며, 그 밖의 버튼이나 modifier 키는 눌려 있지 않다.
  • grab_window가 포인터를 포함한다.
  • confine_to 창(있다면)이 보이는 상태다.
  • grab_window의 조상 창에 같은 버튼/키 조합의 수동 grab이 없다.

나머지 인자는 XGrabPointer와 같은 뜻이다. 이렇게 시작된 능동 grab은 논리적으로 모든 버튼이 놓이면 자동으로 끝난다(modifier 상태와는 무관).

  • button에 AnyButton을 주면 모든 버튼에 대해 등록한 것과 같다. 아니면 그 버튼이 지금 실제 물리 버튼에 할당되어 있지 않아도 된다.
  • modifiers에 AnyModifier를 주면 modifier가 하나도 없는 경우를 포함해 모든 조합에 대해 등록한 것과 같다. 지정한 modifier에 현재 KeyCode가 배정되어 있지 않아도 된다.
  • 같은 클라이언트가 같은 창·같은 조합으로 다시 등록하면 이전 것을 덮어쓴다.
  • 다른 클라이언트가 이미 같은 창·같은 조합을 등록했다면 BadAccess가 난다. AnyModifier/AnyButton을 쓸 때 어느 한 조합이라도 충돌하면 요청 전체가 실패하고 아무 grab도 생기지 않는다.
  • 이미 진행 중인 능동 grab에는 영향이 없다.

XUngrabButton은 이 클라이언트가 등록한 수동 grab을 해제한다. AnyModifier, AnyButton의 뜻은 같다. 진행 중인 능동 grab에는 영향이 없다.

함정: modifier 조합은 "정확히 일치"해야 한다. 조건에 "그 밖의 modifier 키는 눌려 있지 않다"가 있기 때문이다. NumLock이나 CapsLock이 켜져 있으면 그것도 modifier(LockMask, 흔히 NumLock은 Mod2Mask)로 잡혀서, ControlMask만 등록한 grab이 동작하지 않는다. 창 관리자나 단축키 프로그램은 그래서 같은 grab을 LockMask, NumLock 마스크를 섞은 조합마다 여러 번 등록한다.

예제: 고무줄(rubber-band) 사각형 선택

버튼 1을 누르고 끌면 점선 같은 XOR 사각형이 따라오고, 놓으면 고른 영역을 출력하는 예제다. 누르는 순간 XGrabPointer로 포인터를 창 안에 가두고 십자 커서를 보여 준다. 사각형은 GXxor 함수로 그려서, 같은 사각형을 한 번 더 그리면 지워지게 한다.

/* rubber.c : cc rubber.c -lX11 */
#include <X11/Xlib.h>
#include <X11/cursorfont.h>
#include <stdio.h>
#include <stdlib.h>

static void draw_box(Display *d, Window w, GC gc, int x0, int y0, int x1, int y1)
{
    int x = x0 < x1 ? x0 : x1, y = y0 < y1 ? y0 : y1;
    unsigned int wd = abs(x1 - x0), ht = abs(y1 - y0);
    XDrawRectangle(d, w, gc, x, y, wd, ht);
}

int main(void)
{
    Display *d = XOpenDisplay(NULL);
    if (!d) { fprintf(stderr, "cannot open display\n"); return 1; }
    int s = DefaultScreen(d);
    Window w = XCreateSimpleWindow(d, RootWindow(d, s), 0, 0, 400, 300, 1,
                                   BlackPixel(d, s), WhitePixel(d, s));
    XSelectInput(d, w, ExposureMask | ButtonPressMask);
    XMapWindow(d, w);

    XGCValues gv;
    gv.function = GXxor;
    gv.foreground = BlackPixel(d, s) ^ WhitePixel(d, s);
    GC gc = XCreateGC(d, w, GCFunction | GCForeground, &gv);
    Cursor cross = XCreateFontCursor(d, XC_crosshair);

    int dragging = 0, x0 = 0, y0 = 0, x1 = 0, y1 = 0;
    for (;;) {
        XEvent ev;
        XNextEvent(d, &ev);
        switch (ev.type) {
        case ButtonPress:
            if (ev.xbutton.button != Button1 || dragging) break;
            /* 이벤트의 시각을 넘긴다. 창 안에 가두고 십자 커서 */
            if (XGrabPointer(d, w, False,
                             ButtonReleaseMask | PointerMotionMask,
                             GrabModeAsync, GrabModeAsync,
                             w, cross, ev.xbutton.time) != GrabSuccess) {
                fprintf(stderr, "grab failed\n");
                break;
            }
            dragging = 1;
            x0 = x1 = ev.xbutton.x; y0 = y1 = ev.xbutton.y;
            draw_box(d, w, gc, x0, y0, x1, y1);
            break;
        case MotionNotify:
            if (!dragging) break;
            /* 쌓인 MotionNotify는 건너뛰고 마지막 것만 쓴다 */
            while (XCheckTypedWindowEvent(d, w, MotionNotify, &ev))
                ;
            draw_box(d, w, gc, x0, y0, x1, y1);   /* 이전 상자 지우기 */
            x1 = ev.xmotion.x; y1 = ev.xmotion.y;
            draw_box(d, w, gc, x0, y0, x1, y1);   /* 새 상자 */
            break;
        case ButtonRelease:
            if (!dragging || ev.xbutton.button != Button1) break;
            draw_box(d, w, gc, x0, y0, x1, y1);   /* 지우기 */
            XUngrabPointer(d, ev.xbutton.time);
            dragging = 0;
            printf("selected: (%d,%d)-(%d,%d)\n", x0, y0,
                   ev.xbutton.x, ev.xbutton.y);
            break;
        }
    }
}
XOR 그리기는 Expose로 창이 다시 그려지면 짝이 어긋날 수 있다. 실제 프로그램에서는 끌기 도중 Expose가 오면 배경을 다시 그린 뒤 현재 상자를 한 번 그려 상태를 맞춘다. 화면 전체(루트 창)에 고무줄을 그리려면 GC의 subwindow_mode를 IncludeInferiors로 하고, 다른 프로그램이 그 사이에 그려 짝이 깨지지 않게 XGrabServer로 서버를 잠깐 잡는 방법도 쓴다(잡았으면 반드시 XUngrabServer).

12.2 키보드 grab (Keyboard Grabbing)

키보드 쪽도 구조가 포인터와 같다. 능동 grab(XGrabKeyboard)과 수동 grab(XGrabKey)이 있고, modifiers에는 앞의 keymask 비트를 쓴다.

XGrabKeyboard

int XGrabKeyboard(Display *display, Window grab_window, Bool owner_events,
                  int pointer_mode, int keyboard_mode, Time time);

키보드를 지금 바로 능동 grab하고 FocusIn/FocusOut 이벤트를 만든다. 이후 키 이벤트는 grab한 클라이언트에게만 간다.

  • owner_events: False면 모든 키 이벤트가 grab_window 기준으로 보고된다. True면 원래 이 클라이언트에게 갈 이벤트는 평소대로, 아니면 grab_window 기준으로 보고된다.
  • 포인터 grab과 다른 점: event_mask가 없다. KeyPress와 KeyRelease는 클라이언트가 이벤트를 골랐는지와 상관없이 항상 보고된다.
  • Sync/Async 의미는 포인터 grab과 같다. 다만 얼림은 XAllowEvents를 부르거나 키보드 grab이 풀릴 때 풀린다.

실패 반환값은 AlreadyGrabbed(다른 클라이언트가 grab 중), GrabNotViewable(grab_window가 안 보임), GrabFrozen(다른 클라이언트 grab 때문에 얼어 있음), GrabInvalidTime(시각 조건 불만족)이다. 성공하면 마지막 키보드 grab 시각이 갱신된다. BadValue, BadWindow 오류가 날 수 있다.

키보드를 grab한 채 프로그램이 죽거나 무한 루프에 빠지면 사용자는 키보드를 전혀 쓸 수 없다(연결이 끊기면 서버가 풀어 주긴 한다). 팝업 메뉴, 암호 입력창처럼 꼭 필요한 짧은 구간에만 쓰고, 끝나면 반드시 XUngrabKeyboard를 부른다.

XUngrabKeyboard

XUngrabKeyboard(Display *display, Time time);

XGrabKeyboard나 XGrabKey로 얻은 능동 grab과 쌓인 이벤트를 풀어 준다. time 조건이 맞지 않으면 아무 일도 하지 않는다. FocusIn/FocusOut이 생긴다. 능동 키보드 grab의 이벤트 창이 보이지 않게 되면 서버가 자동으로 푼다.

XGrabKey / XUngrabKey

XGrabKey(Display *display, int keycode, unsigned int modifiers,
         Window grab_window, Bool owner_events,
         int pointer_mode, int keyboard_mode);

XUngrabKey(Display *display, int keycode, unsigned int modifiers,
           Window grab_window);

키 하나에 수동 grab을 건다. 전역 단축키를 만들 때 흔히 쓴다. 다음 조건이 모두 맞으면 키보드가 능동 grab되고 그 KeyPress가 보고된다.

  • 키보드가 grab되어 있지 않고, 지정한 modifier가 눌린 상태에서 지정한 키(modifier 키 자체여도 됨)가 눌렸으며, 다른 modifier는 눌려 있지 않다.
  • grab_window가 포커스 창이거나 그 조상이다. 또는 grab_window가 포커스 창의 자손이면서 포인터를 포함한다.
  • grab_window의 조상에 같은 키 조합의 수동 grab이 없다.

이 능동 grab은 그 키가 놓이면 자동으로 끝난다. AnyModifier, AnyKey는 버튼 쪽과 같은 뜻이다. AnyKey가 아니면 keycode는 접속 시 알려 준 min_keycode~max_keycode 범위여야 하고, 아니면 BadValue가 난다. 다른 클라이언트가 같은 창·같은 조합을 이미 잡았으면 BadAccess가 나고, AnyModifier/AnyKey에서 충돌이 하나라도 있으면 전체가 실패한다.

XUngrabKey는 이 클라이언트가 건 수동 grab을 해제하고, 진행 중인 능동 grab에는 영향이 없다.

/* 루트 창에 Ctrl+Alt+T 전역 단축키 걸기 (NumLock/CapsLock 조합까지) */
#include <X11/Xlib.h>
#include <X11/keysym.h>

void grab_hotkey(Display *d, Window root)
{
    KeyCode kc = XKeysymToKeycode(d, XK_t);
    unsigned int base = ControlMask | Mod1Mask;
    unsigned int extra[] = { 0, LockMask, Mod2Mask, LockMask | Mod2Mask };
    for (int i = 0; i < 4; i++)
        XGrabKey(d, kc, base | extra[i], root, True,
                 GrabModeAsync, GrabModeAsync);
    XSelectInput(d, root, KeyPressMask);
}
함정 1: XGrabKey는 KeySym이 아니라 KeyCode를 받는다. XKeysymToKeycode로 바꿔서 넘긴다. 함정 2: 다른 프로그램이 이미 같은 조합을 잡았으면 BadAccess가 비동기 오류로 나중에 와서 기본 오류 처리기가 프로그램을 끝낸다. 실패를 견디려면 XSetErrorHandler로 처리기를 바꾸고 XSync로 결과를 확인한다. NumLock이 Mod2Mask라는 것은 흔한 설정일 뿐 보장은 아니다(12.7의 modifier 매핑으로 확인 가능).

12.3 이벤트 처리 재개 (Resuming Event Processing)

동기 모드 grab으로 얼린 장치를 다시 움직이게 하는 함수가 XAllowEvents다.

XAllowEvents(Display *display, int event_mode, Time time);

클라이언트가 얼린 장치의 쌓인 이벤트 일부 또는 전부를 풀어 준다. time이 이 클라이언트의 가장 최근 능동 grab 시각보다 이르거나 현재 서버 시각보다 늦으면 아무 효과가 없다.

event_mode동작
AsyncPointer이 클라이언트가 얼린 포인터를 평소대로 계속 처리한다. 두 개의 grab 때문에 두 번 얼었어도 둘 다 푼다. 포인터를 grab하고 있지 않아도 되지만, 얼려 둔 것이 없으면 효과 없음.
SyncPointer포인터가 이 클라이언트에 의해 얼고 grab된 상태일 때, 다음 ButtonPress나 ButtonRelease가 클라이언트에 보고될 때까지만 처리하고 다시 언다. 그 이벤트로 grab이 풀리면 얼지 않는다. "이벤트 하나씩 받아 보기"에 쓴다.
ReplayPointer포인터가 이벤트 때문에 얼어 있을 때(XGrabButton 활성화나 앞선 SyncPointer 때문, XGrabPointer 때문은 아님) grab을 풀고 그 이벤트를 처음부터 다시 처리한다. 이때 방금 푼 grab의 grab_window와 그 위(루트 쪽) 창들의 수동 grab은 무시한다. 즉 "나는 이 클릭이 필요 없으니 원래 받을 창에 보내라"는 뜻이다.
AsyncKeyboard키보드에 대한 AsyncPointer.
SyncKeyboard키보드에 대한 SyncPointer(KeyPress/KeyRelease 기준).
ReplayKeyboard키보드에 대한 ReplayPointer(XGrabKey 또는 앞선 SyncKeyboard 때문에 언 경우).
SyncBoth두 장치가 모두 이 클라이언트에 의해 얼었을 때, grab된 장치에 대해 다음 버튼·키 이벤트가 보고될 때까지 둘 다 처리하고 다시 둘 다 언다. 그 이벤트로 grab이 풀리면 얼지 않지만, 다른 장치가 아직 grab 중이면 그 장치의 다음 이벤트가 둘 다 얼린다. 둘 다 얼어 있지 않으면 효과 없음.
AsyncBoth두 장치가 모두 얼어 있을 때 둘 다 평소대로 처리한다. 둘 다 얼어 있지 않으면 효과 없음.

Pointer 계열 모드는 키보드에, Keyboard 계열 모드는 포인터에 영향을 주지 않는다. 포인터 grab과 키보드 grab은 (같은 클라이언트든 다른 클라이언트든) 동시에 있을 수 있다. 한 장치가 두 grab 모두 때문에 얼어 있으면, 두 쪽 모두에서 풀어야 이벤트가 다시 흐른다. 한 클라이언트가 같은 장치를 두 번 얼렸다면 XAllowEvents 한 번으로 둘 다 풀린다. BadValue 오류가 날 수 있다.

/* 창 관리자식 "클릭하면 포커스 주고 클릭은 앱에 넘기기" */
XGrabButton(d, AnyButton, AnyModifier, frame, False,
            ButtonPressMask, GrabModeSync, GrabModeAsync, None, None);
...
case ButtonPress:
    XSetInputFocus(d, client_win, RevertToParent, ev.xbutton.time);
    XRaiseWindow(d, frame);
    XAllowEvents(d, ReplayPointer, ev.xbutton.time);  /* 클릭을 앱에 다시 보냄 */
    break;
Sync 모드로 grab하고 XAllowEvents를 잊으면 포인터가 그대로 얼어 화면 전체 마우스가 멈춘 것처럼 보인다. Sync를 쓴 경로에는 반드시 Allow나 Ungrab이 있는지 확인한다.

12.4 포인터 옮기기 (Moving the Pointer)

XWarpPointer(Display *display, Window src_w, Window dest_w,
             int src_x, int src_y, unsigned int src_width, unsigned int src_height,
             int dest_x, int dest_y);

포인터를 프로그램이 옮긴다.

  • dest_w가 None이면 현재 위치에서 (dest_x, dest_y)만큼 상대 이동한다.
  • dest_w가 창이면 그 창의 원점 기준 (dest_x, dest_y)로 옮긴다.
  • src_w가 창이면, 포인터가 src_w 안에 있고 그 안의 지정한 사각형(src_x, src_y, src_width, src_height, src_w 원점 기준) 안에 있을 때만 옮긴다. src_width/src_height가 0이면 각각 "창 너비 − src_x", "창 높이 − src_y"로 바뀐다.

원문도 강조하듯 이 함수를 쓸 이유는 거의 없다. 포인터는 사용자에게 맡기는 것이 원칙이다. 쓰면 사용자가 순간적으로 포인터를 옮긴 것과 똑같이 이벤트가 생긴다. 능동 grab의 confine_to 창 밖으로는 옮길 수 없고, 시도하면 가장 가까운 가장자리까지만 간다. BadWindow 오류가 날 수 있다.

/* 게임: 매 프레임 포인터를 창 가운데로 되돌려 상대 움직임만 읽기 */
XWarpPointer(d, None, w, 0, 0, 0, 0, width / 2, height / 2);

12.5 입력 포커스 제어 (Controlling Input Focus)

입력 포커스(키보드 입력이 갈 창)는 모든 클라이언트가 함께 쓰는 자원이라 서로 협조해야 한다. 포커스 정책은 ICCCM이 정한다(14장의 XWMHints.input 참고).

XSetInputFocus(Display *display, Window focus, int revert_to, Time time);

입력 포커스와 마지막 포커스 변경 시각을 바꾼다. time이 마지막 포커스 변경 시각보다 이르거나 현재 서버 시각보다 늦으면 효과가 없다. FocusIn/FocusOut 이벤트가 생긴다.

  • focus가 None: 새 포커스가 정해질 때까지 모든 키보드 이벤트를 버린다. revert_to는 무시.
  • focus가 창: 그 창이 키보드 포커스 창이 된다. 원래 그 창이나 하위 창으로 갈 키 이벤트는 평소대로 보고되고, 그 밖의 이벤트는 포커스 창 기준으로 보고된다.
  • focus가 PointerRoot: 키 이벤트마다 포인터가 있는 화면의 루트 창을 포커스로 본다. 결과적으로 "포인터 밑 창이 키 입력을 받는" 방식이 된다. revert_to는 무시.

지정한 창은 호출 시점에 보이는 상태여야 하며, 아니면 BadMatch가 난다. 나중에 그 창이 안 보이게 되면 revert_to로 새 포커스를 정한다.

revert_to포커스 창이 사라지면
RevertToParent부모(또는 가장 가까운 보이는 조상)로 옮기고, 새 revert_to는 RevertToNone이 된다.
RevertToPointerRootPointerRoot로.
RevertToNoneNone으로.

되돌아갈 때도 FocusIn/FocusOut이 생기지만 마지막 포커스 변경 시각은 바뀌지 않는다. BadMatch, BadValue, BadWindow 오류가 날 수 있다.

XGetInputFocus(Display *display, Window *focus_return, int *revert_to_return);

현재 포커스 창(또는 PointerRoot, None)과 revert_to 상태를 돌려준다.

가장 흔한 실수: 창을 XMapWindow한 직후 바로 XSetInputFocus를 부르면 창이 아직 viewable이 아니어서 BadMatch로 프로그램이 끝난다. MapNotify(또는 첫 Expose)를 받은 뒤에 부른다. 또 창 관리자 아래의 보통 앱은 직접 포커스를 뺏기보다 창 관리자에게 맡기는 것이 원칙이다.

12.6 키보드·포인터 설정 (Manipulating the Keyboard and Pointer Settings)

벨, 키 클릭, 자동 반복, LED, 포인터 가속 같은 사용자 취향 설정을 바꾸는 함수들이다. 기본값은 서버마다 다르고, 모든 서버가 모든 항목을 실제로 제어할 수 있는 것은 아니다. 대부분 사용자 설정 도구(xset 같은 것)가 쓰고, 일반 앱이 바꿀 일은 드물다.

XChangeKeyboardControl / XGetKeyboardControl

XChangeKeyboardControl(Display *display, unsigned long value_mask,
                       XKeyboardControl *values);
XGetKeyboardControl(Display *display, XKeyboardState *values_return);

/* value_mask 비트 */
KBKeyClickPercent KBBellPercent KBBellPitch KBBellDuration
KBLed KBLedMode KBKey KBAutoRepeatMode

typedef struct {
    int key_click_percent;
    int bell_percent;
    int bell_pitch;
    int bell_duration;
    int led;
    int led_mode;          /* LedModeOn, LedModeOff */
    int key;
    int auto_repeat_mode;  /* AutoRepeatModeOff, AutoRepeatModeOn,
                              AutoRepeatModeDefault */
} XKeyboardControl;
  • key_click_percent, bell_percent: 0(끔)~100(크게) 음량. -1이면 기본값 복원, 그 밖의 음수는 BadValue.
  • bell_pitch(Hz), bell_duration(밀리초): -1이면 기본값, 다른 음수는 BadValue.
  • led + led_mode: 둘 다 주면 그 LED 하나를, led_mode만 주면 모든 LED를 바꾼다. LED는 1번부터 최대 32개이고 표준 의미는 없다. led만 주고 led_mode가 없으면 BadMatch.
  • key + auto_repeat_mode: 둘 다 주면 그 키 하나의 자동 반복 모드를 바꾸고, auto_repeat_mode만 주면 키보드 전체의 전역 모드를 바꾼다(키별 설정은 그대로). key만 주면 BadMatch.

자동 반복은 두 층으로 되어 있다. 키마다 개별 모드가 있고, 전체를 켜고 끄는 전역 모드가 있다. 전역 모드가 On이면 각 키는 자기 개별 모드를 따르고, Off면 어떤 키도 반복하지 않는다. 자동 반복되는 키는 KeyPress와 KeyRelease를 번갈아 만든다. modifier로 쓰이는 키는 설정과 관계없이 반복하지 않는 것이 바람직하다. 검사·변경 순서는 서버마다 다르므로, 오류가 나면 일부 항목만 바뀌었을 수 있다.

XGetKeyboardControl은 현재 값을 XKeyboardState로 돌려준다.

typedef struct {
    int key_click_percent;
    int bell_percent;
    unsigned int bell_pitch, bell_duration;
    unsigned long led_mask;     /* 최하위 비트 = LED 1, 1이면 켜짐 */
    int global_auto_repeat;     /* AutoRepeatModeOn / Off */
    char auto_repeats[32];      /* 키별 자동 반복 비트 벡터 */
} XKeyboardState;

auto_repeats는 32바이트 비트 벡터다. N번째 바이트(0부터)는 키 8N~8N+7을 나타내고, 바이트의 최하위 비트가 키 8N이다.

게임에서 "키를 누르고 있는 동안" 처리를 하려고 전역 자동 반복을 끄는(XAutoRepeatOff) 경우가 있는데, 이것은 서버 전체 설정이라 프로그램이 죽으면 다른 모든 앱에서도 반복이 꺼진 채로 남는다. 보통은 KeyRelease 직후 같은 시각의 KeyPress가 오는지 보고 반복을 걸러 내는 편이 낫다.

자동 반복, 벨

XAutoRepeatOn(Display *display);
XAutoRepeatOff(Display *display);
XBell(Display *display, int percent);

XAutoRepeatOn/Off는 키보드 자동 반복을 켜고 끈다. XBell은 키보드 벨을 울린다. percent는 -100~100이고 범위를 벗어나면 BadValue다. 음량은 기본 음량(base)에 대해 상대적으로 정해진다.

  • percent ≥ 0: base - [(base * percent) / 100] + percent
  • percent < 0: base + [(base * percent) / 100]

즉 100이면 최대 음량, 0이면 기본 음량, -100이면 무음이다. 기본 음량 자체는 XChangeKeyboardControl로 바꾼다.

XQueryKeymap

XQueryKeymap(Display *display, char keys_return[32]);

지금 눌려 있는 키들을 32바이트 비트 벡터로 돌려준다(형식은 auto_repeats와 같음). 키보드 처리가 얼어 있으면 논리적 상태가 실제보다 늦을 수 있다.

char keys[32];
XQueryKeymap(d, keys);
KeyCode kc = XKeysymToKeycode(d, XK_space);
int down = (keys[kc / 8] >> (kc % 8)) & 1;

포인터 버튼 매핑

int XSetPointerMapping(Display *display, unsigned char map[], int nmap);
int XGetPointerMapping(Display *display, unsigned char map_return[], int nmap);

XSetPointerMapping은 물리 버튼과 논리 버튼 번호의 대응을 바꾼다. map[i]는 물리 버튼 i+1의 논리 번호다. 목록 길이는 XGetPointerMapping이 돌려줄 길이와 같아야 하고(아니면 BadValue), 0은 버튼을 끈다. 0이 아닌 같은 값이 두 번 나오면 BadValue다. 성공하면 MappingNotify가 생기고 MappingSuccess를 돌려주며, 바꾸려는 버튼이 지금 눌려 있으면 MappingBusy를 돌려주고 아무것도 바꾸지 않는다. 왼손잡이용으로 1번과 3번을 맞바꾸는 것이 대표적인 쓰임이다.

XGetPointerMapping은 현재 매핑을 앞의 nmap개까지 채워 주고, 실제 물리 버튼 수를 돌려준다. 기본 매핑은 map[i] = i+1이다.

포인터 가속

XChangePointerControl(Display *display, Bool do_accel, Bool do_threshold,
                      int accel_numerator, int accel_denominator, int threshold);
XGetPointerControl(Display *display, int *accel_numerator_return,
                   int *accel_denominator_return, int *threshold_return);

가속은 분수로 된 이동 배율이다. 3/1이면 세 배 빠르게 움직인다(서버가 분수를 임의로 반올림할 수 있음). 가속은 한 번에 threshold 픽셀보다 많이 움직일 때만, 그것도 threshold를 넘는 부분에만 적용된다. 값 -1은 기본값 복원이다. do_accel, do_threshold가 True여야 해당 값이 적용된다. -1이 아닌 음수나 분모 0은 BadValue다. XGetPointerControl은 현재 배율과 threshold를 돌려준다.

12.7 키보드 인코딩 (Manipulating the Keyboard Encoding)

KeyCode와 KeySym

X는 키를 두 단계로 나눠 표현한다.

  • KeyCode: 물리적(또는 논리적) 키 하나를 가리키는 번호다. 범위는 8~255이고 숫자 자체에는 의미가 없다(서버가 키보드 배열 정보를 담으려 할 수는 있다). 키와 KeyCode의 대응은 바꿀 수 없다.
  • KeySym: 키 위에 새겨진 기호를 나타내는 코드다. ISO Latin 1~4, 가타카나, 아랍, 키릴, 그리스, 기술 기호, 특수, 출판, APL, 히브리, 타이, 한국어 문자 집합과 Return, Help, Tab 같은 키들이 정의되어 있다. 목록은 <X11/keysymdef.h>에 있고, 대부분의 앱은 Latin 1~4, 그리스, 기타 키만 정의한 <X11/keysym.h>만 포함한다(일부 C 전처리기는 정의할 수 있는 기호 수에 한계가 있기 때문).

왜 둘로 나누는가? 같은 위치의 키라도 나라별 키보드마다 새겨진 글자가 다르기 때문이다. 앱은 KeyCode가 아니라 KeySym으로 판단해야 키보드 배열에 상관없이 동작한다. 중요한 점: X 서버 자신은 KeyCode→KeySym 대응을 쓰지 않는다. 그냥 저장해 두고 클라이언트들이 읽고 쓰게 할 뿐이다. 실제 해석은 Xlib(클라이언트 쪽)이 한다.

KeySym 목록과 그룹

KeyCode마다 KeySym 목록이 붙어 있다. 뒤쪽의 NoSymbol을 무시했을 때 목록이

  • K 하나면 "K NoSymbol K NoSymbol"로,
  • K1 K2 두 개면 "K1 K2 K1 K2"로,
  • K1 K2 K3 세 개면 "K1 K2 K3 NoSymbol"로 본다.

일부러 빈칸을 두고 싶으면 VoidSymbol을 쓴다. 처음 네 개는 두 그룹으로 나뉜다. 그룹 1은 1·2번째, 그룹 2는 3·4번째다. 한 그룹의 두 번째가 NoSymbol이면 첫 번째와 같다고 본다. 단, 첫 번째가 대소문자가 있는 알파벳 K라면 첫 번째는 소문자 K, 두 번째는 대문자 K로 본다. 그래서 키보드 매핑에는 'a' 하나만 적어 두어도 Shift+a가 'A'가 된다.

KeyPress에서 KeySym을 고르는 표준 규칙은 그룹 1, 2만 쓴다. 어느 그룹을 쓸지는 modifier 상태로 정한다.

  • 그룹 modifier: MODE SWITCH라는 KeySym을 어떤 KeyCode에 붙이고, 그 KeyCode를 Mod1~Mod5 중 하나에 붙이면 그 modifier가 그룹 modifier가 된다. 꺼져 있으면 그룹 1, 켜져 있으면 그룹 2를 쓴다.
  • Lock: XK_Caps_Lock이 붙은 KeyCode가 Lock modifier에 붙어 있으면 CapsLock으로, XK_Shift_Lock이면 ShiftLock으로 해석한다. 둘 다 가능하면 CapsLock으로 본다.
  • numlock modifier: XK_Num_Lock이 붙은 KeyCode가 Mod1~Mod5 중 하나에 붙어 있으면 그것이 numlock modifier다. 이름이 "XK_KP_"로 시작하는 KeySym(값 0xFF80~0xFFBD)과 벤더 범위 0x11000000~0x1100FFFF가 키패드 KeySym이다.

그룹 안에서는 다음 규칙 중 처음 맞는 것을 쓴다.

  1. numlock이 켜져 있고 두 번째 KeySym이 키패드 KeySym이면: Shift가 켜져 있거나 Lock이 ShiftLock으로 켜져 있으면 첫 번째, 아니면 두 번째.
  2. Shift와 Lock이 모두 꺼져 있으면: 첫 번째.
  3. Shift는 꺼져 있고 Lock이 CapsLock으로 켜져 있으면: 첫 번째. 단, 그것이 소문자 알파벳이면 대문자로.
  4. Shift가 켜져 있고 Lock이 CapsLock으로 켜져 있으면: 두 번째. 단, 그것이 소문자 알파벳이면 대문자로.
  5. Shift가 켜져 있거나 Lock이 ShiftLock으로 켜져 있거나 둘 다면: 두 번째.

목록의 순서는 키 위 기호의 공간적 배치를 뜻하지 않는다. 이 규칙을 앱이 직접 구현할 필요는 없고, 16장의 XLookupString이 대신 해 준다.

KeyCode 범위와 매핑 읽기·쓰기

XDisplayKeycodes(Display *display, int *min_keycodes_return, int *max_keycodes_return);

KeySym *XGetKeyboardMapping(Display *display, KeyCode first_keycode,
                            int keycode_count, int *keysyms_per_keycode_return);

XChangeKeyboardMapping(Display *display, int first_keycode, int keysyms_per_keycode,
                       KeySym *keysyms, int num_codes);

XDisplayKeycodes는 이 디스플레이가 쓰는 최소·최대 KeyCode를 돌려준다. 최소는 8 이상, 최대는 255 이하이며 범위 안의 모든 KeyCode에 실제 키가 있어야 하는 것은 아니다.

XGetKeyboardMapping은 first_keycode부터 keycode_count개의 KeySym 목록을 돌려준다. first_keycode는 min_keycode 이상, first_keycode + keycode_count - 1은 max_keycode 이하여야 하며 아니면 BadValue다. 돌려받는 배열은 1차원으로, 원소 수는 keycode_count * keysyms_per_keycode_return이고, KeyCode K의 N번째(0부터) KeySym은 (K - first_keycode) * keysyms_per_keycode_return + N 위치에 있다. 키당 개수는 서버가 모든 기호를 담을 만큼 정하고 빈칸은 NoSymbol로 채운다. 다 쓰면 XFree로 해제한다.

int minkc, maxkc, per;
XDisplayKeycodes(d, &minkc, &maxkc);
KeySym *map = XGetKeyboardMapping(d, minkc, maxkc - minkc + 1, &per);
for (int k = minkc; k <= maxkc; k++) {
    KeySym ks = map[(k - minkc) * per + 0];
    if (ks != NoSymbol)
        printf("%3d: %s\n", k, XKeysymToString(ks));
}
XFree(map);

XChangeKeyboardMapping은 first_keycode부터 num_codes개 KeyCode의 기호를 바꾼다(범위 밖은 그대로). keysyms 배열 원소 수는 num_codes * keysyms_per_keycode이고 인덱스 계산은 위와 같다. 범위 조건도 같다. 키당 개수는 클라이언트가 마음대로 정하며, 중간에 NoSymbol이 와도 된다. MappingNotify를 만들고, BadAlloc, BadValue 오류가 날 수 있다. 서버는 이 매핑을 해석하지 않고 저장만 한다.

modifier 매핑 (XModifierKeymap)

어떤 KeyCode들이 Shift, Lock, Control, Mod1~Mod5 역할을 하는지 정하는 표다.

typedef struct {
    int max_keypermod;     /* 이 서버에서 modifier 하나당 최대 키 수 */
    KeyCode *modifiermap;  /* 8 x max_keypermod 배열 */
} XModifierKeymap;

XModifierKeymap *XNewModifiermap(int max_keys_per_mod);
XModifierKeymap *XInsertModifiermapEntry(XModifierKeymap *modmap,
                                         KeyCode keycode_entry, int modifier);
XModifierKeymap *XDeleteModifiermapEntry(XModifierKeymap *modmap,
                                         KeyCode keycode_entry, int modifier);
XFreeModifiermap(XModifierKeymap *modmap);
int XSetModifierMapping(Display *display, XModifierKeymap *modmap);
XModifierKeymap *XGetModifierMapping(Display *display);
  • XNewModifiermap: modifier당 KeyCode 칸을 미리 잡아 새 구조체를 만든다.
  • XInsertModifiermapEntry: KeyCode를 해당 modifier 집합에 추가하고 (필요하면 늘린) 결과 구조체를 돌려준다. 돌려받은 포인터를 계속 써야 한다.
  • XDeleteModifiermapEntry: KeyCode를 집합에서 뺀 결과를 돌려준다.
  • XFreeModifiermap: 구조체를 해제한다.
  • XSetModifierMapping: modifier로 쓸 KeyCode들을 서버에 설정한다. modifiermap은 Shift, Lock, Control, Mod1, Mod2, Mod3, Mod4, Mod5 순서로 max_keypermod개씩 들어 있고, 0인 칸은 무시한다. modifier는 최대 8개이며 더 많으면 BadLength, KeyCode가 min~max 범위 밖이면 BadValue다. 성공하면 MappingNotify가 생기고 MappingSuccess를 돌려준다. 서버가 제약(하드웨어가 키 놓기를 알려 주지 못함, 자동 반복을 끌 수 없음, 여러 modifier 키 미지원 등)을 어기면 MappingFailed, 바뀌는 modifier의 현재 또는 새 키가 눌려 있으면 MappingBusy를 돌려주고 아무것도 바꾸지 않는다.
  • XGetModifierMapping: 현재 modifier 매핑을 새로 만들어 돌려준다. XFreeModifiermap으로 해제한다. 어떤 modifier의 집합이 모두 0이면 그 modifier는 꺼진 것이다.
/* NumLock이 어떤 Mod 비트인지 알아내기 */
unsigned int numlock_mask(Display *d)
{
    XModifierKeymap *mm = XGetModifierMapping(d);
    KeyCode nl = XKeysymToKeycode(d, XK_Num_Lock);
    unsigned int mask = 0;
    for (int m = 0; m < 8; m++)
        for (int k = 0; k < mm->max_keypermod; k++)
            if (nl && mm->modifiermap[m * mm->max_keypermod + k] == nl)
                mask = 1u << m;     /* ShiftMask=1<<0 ... Mod5Mask=1<<7 */
    XFreeModifiermap(mm);
    return mask;
}
키보드나 modifier 매핑이 바뀌면 모든 클라이언트에 MappingNotify가 온다(이 이벤트는 고르지 않아도 항상 온다). Xlib은 매핑을 캐시하므로, 받으면 XRefreshKeyboardMapping(16장)을 불러 캐시를 갱신한다. 위 예처럼 직접 계산한 마스크도 다시 계산해야 한다.
