11장. 이벤트 처리 함수 (Event Handling Functions)

이 장은 이벤트를 고르고(select), 출력 버퍼와 이벤트 큐를 다루고, 큐에서 이벤트를 꺼내고, 다른 프로그램에 이벤트를 보내고, 프로토콜 오류를 처리하는 Xlib 함수를 다룬다.

일부 툴킷(Xt, GTK, Qt 등)은 자체 이벤트 처리 함수를 쓰므로 이 장의 Xlib 함수와 섞어 쓰면 안 될 수 있다. 툴킷 문서를 따른다.

대부분의 X 앱은 그냥 하나의 이벤트 루프다. 이벤트를 기다리고, 무엇을 할지 정하고, 화면을 바꾸는 코드를 조금 실행하고, 다시 다음 이벤트를 기다린다. 먼저 전체 그림을 잡기 위해 가장 기본적인 프로그램을 보자.

/* cc ev.c -lX11 */
#include <X11/Xlib.h>
#include <X11/Xutil.h>
#include <stdio.h>

int main(void) {
    Display *dpy = XOpenDisplay(NULL);
    if (!dpy) { fprintf(stderr, "cannot open %s\n", XDisplayName(NULL)); return 1; }
    int scr = DefaultScreen(dpy);
    Window win = XCreateSimpleWindow(dpy, RootWindow(dpy, scr), 0, 0, 300, 200, 1,
                                     BlackPixel(dpy, scr), WhitePixel(dpy, scr));
    XSelectInput(dpy, win, ExposureMask | KeyPressMask | ButtonPressMask
                           | StructureNotifyMask);
    Atom wm_delete = XInternAtom(dpy, "WM_DELETE_WINDOW", False);
    XSetWMProtocols(dpy, win, &wm_delete, 1);
    XMapWindow(dpy, win);
    GC gc = DefaultGC(dpy, scr);

    for (int running = 1; running; ) {
        XEvent ev;
        XNextEvent(dpy, &ev);              /* 큐가 비면 flush 후 대기 */
        switch (ev.type) {
        case Expose:
            if (ev.xexpose.count == 0)
                XDrawString(dpy, win, gc, 20, 40, "press q", 7);
            break;
        case KeyPress: {
            char buf[8]; KeySym ks;
            int n = XLookupString(&ev.xkey, buf, sizeof buf, &ks, NULL);
            if (n == 1 && buf[0] == 'q') running = 0;
            break;
        }
        case ButtonPress:
            printf("button %u (%d,%d)\n", ev.xbutton.button, ev.xbutton.x, ev.xbutton.y);
            break;
        case ClientMessage:
            if ((Atom)ev.xclient.data.l[0] == wm_delete) running = 0;
            break;
        case MappingNotify:
            XRefreshKeyboardMapping(&ev.xmapping);
            break;
        }
    }
    XCloseDisplay(dpy);
    return 0;
}

11.1 이벤트 고르기

받을 이벤트를 정하는 방법은 두 가지다. XCreateWindow나 XChangeWindowAttributes를 부를 때 XSetWindowAttributes의 event_mask 멤버를 설정하는 방법, 그리고 XSelectInput을 쓰는 방법이다.

XSelectInput(Display *display, Window w, long event_mask);

창 w에 대해 event_mask에 해당하는 이벤트를 보고해 달라고 서버에 요청한다.

  • w: 관심 있는 창.
  • event_mask: 10.3절의 마스크들을 OR한 값.

처음에는 아무 이벤트도 보고되지 않는다. 이벤트는 창 기준으로 보고된다. 어떤 창이 장치 이벤트에 관심이 없으면, do_not_propagate 마스크가 막지 않는 한 그 이벤트는 보통 관심 있는 가장 가까운 조상으로 전파된다.

이벤트 마스크 설정은 같은 클라이언트의 같은 창에 대한 이전 설정을 덮어쓴다(더하는 것이 아니다). 다른 클라이언트의 설정에는 영향이 없다. 여러 클라이언트가 같은 창의 같은 이벤트를 고를 수 있고, 서버는 이벤트를 관심 있는 모든 클라이언트에게 보낸다. 다만 다음은 한 번에 한 클라이언트만 고를 수 있다.

  • SubstructureRedirectMask(CirculateRequest, ConfigureRequest, MapRequest)
  • ResizeRedirectMask(ResizeRequest)
  • ButtonPressMask(ButtonPress)

이미 다른 클라이언트가 고른 것을 고르려 하면 BadAccess 오류가 난다(11.8절 오류 표). XSelectInput은 BadWindow 오류도 낼 수 있다.

함정: 마스크를 나눠서 XSelectInput(dpy, w, KeyPressMask); XSelectInput(dpy, w, ExposureMask);처럼 두 번 부르면 마지막 것만 남는다. 필요한 마스크를 한 번에 OR해서 넘기거나, 나중에 추가하려면 현재 마스크(XGetWindowAttributes의 your_event_mask)에 OR해서 다시 설정한다.

11.2 출력 버퍼 다루기

Xlib은 요청을 부를 때마다 바로 네트워크로 보내지 않고 출력 버퍼에 모았다가 한꺼번에 보낸다. 요청마다 시스템 호출을 하면 느리기 때문이다. 이 절의 함수들은 블록(대기)해야 하거나 이벤트를 돌려주지 못할 때 출력 버퍼를 비운다(flush: 아직 안 보낸 요청을 모두 서버로 보냄).

XFlush(Display *display);

출력 버퍼를 비운다. 대부분의 앱은 직접 부를 필요가 없다. XPending, XNextEvent, XWindowEvent 등이 필요할 때 자동으로 비우기 때문이다. 서버가 만든 이벤트는 라이브러리의 이벤트 큐에 들어갈 수 있다.

직접 XFlush가 필요한 대표 경우: 이벤트를 기다리지 않는 루프(게임 루프, 애니메이션)에서 그리기 요청을 보낸 뒤 sleep하는 경우. flush하지 않으면 그림이 버퍼에 머물러 화면에 안 나온다.
XSync(Display *display, Bool discard);

출력 버퍼를 비운 뒤, 서버가 모든 요청을 받고 처리할 때까지 기다린다(왕복 한 번). 그동안 생긴 오류는 모두 오류 처리기로 처리된다. Xlib이 받은 프로토콜 오류마다 앱의 오류 처리 함수를 부른다(11.8.2절). 서버가 만든 이벤트는 큐에 들어간다.

  • discard가 False: 큐의 이벤트를 그대로 둔다.
  • discard가 True: XSync를 부르기 전부터 있던 것을 포함해 큐의 모든 이벤트를 버린다.

앱이 XSync를 부를 일은 드물다. 주로 "이 요청이 오류를 냈는지 지금 확인하고 싶을 때"(아래 오류 처리 예)나 디버깅에 쓴다.

XSync는 서버와 왕복하므로 원격 연결에서 비싸다. 루프 안에서 매번 부르면 크게 느려진다. 또 XSync(dpy, True)는 Expose 같은 중요한 이벤트까지 버리므로 조심한다.

11.3 이벤트 큐 관리

Xlib은 이벤트 큐를 갖고 있다. 그런데 운영체제도 네트워크 연결에 아직 큐로 읽어 들이지 않은 데이터를 버퍼링하고 있을 수 있다. 그래서 "이벤트가 몇 개 있나?"라는 질문에도 "Xlib 큐만 볼지, 소켓도 읽어 볼지, 그 전에 flush할지"의 선택이 있다.

int XEventsQueued(Display *display, int mode);

큐에 있는 이벤트 수를 돌려준다. mode에 따라 동작이 다르다.

mode큐에 이벤트가 있을 때큐가 비었을 때
QueuedAlready그 개수0. 시스템 호출을 절대 하지 않음(XQLength와 같음)
QueuedAfterFlush그 개수출력 버퍼를 비우고, 연결에서 이벤트를 더 읽어 보고, 읽은 수를 돌려줌(XPending과 같음)
QueuedAfterReading그 개수flush 없이 연결에서 더 읽어 보고, 읽은 수를 돌려줌

큐에 이벤트가 이미 있으면 어떤 mode든 입출력 없이 바로 돌아온다. 이 함수들은 블록하지 않는다(읽을 데이터가 없으면 0).

int XPending(Display *display);

서버에서 받았지만 아직 큐에서 꺼내지 않은 이벤트 수를 돌려준다. XEventsQueued(display, QueuedAfterFlush)와 같다. "블록하지 않고 이벤트가 있는지 확인"할 때 가장 흔히 쓴다.

게임처럼 이벤트가 없어도 계속 돌아야 하는 루프의 기본형:

while (running) {
    while (XPending(dpy) > 0) {         /* 쌓인 이벤트를 모두 처리 */
        XEvent ev;
        XNextEvent(dpy, &ev);            /* 이벤트가 있으니 블록하지 않음 */
        handle(&ev);
    }
    update_game();
    draw_frame();                        /* XFillRectangle 등 */
    XFlush(dpy);                         /* 그린 것을 서버로 */
    usleep(16000);                       /* 약 60fps */
}
더 나은 방법: ConnectionNumber(dpy)로 소켓 파일 디스크립터를 얻어 select()/poll()로 타임아웃과 함께 기다리면 CPU를 덜 쓴다. 이때 주의할 점은, Xlib이 이미 큐에 읽어 둔 이벤트는 소켓에 남아 있지 않으므로 select() 전에 반드시 XPending으로 큐를 먼저 비워야 한다는 것이다. 안 그러면 이벤트가 큐에 있는데도 select()에서 멈춘다.

11.4 이벤트 큐 조작

Xlib은 큐에서 이벤트를 꺼내는 여러 함수를 준다. 순서대로 꺼내기, 꺼내지 않고 엿보기, 마스크나 직접 만든 조건(predicate) 함수와 맞는 것만 골라 꺼내기가 있다. 먼저 전체를 비교해 두자.

함수고르는 기준큐에서 제거없으면
XNextEvent맨 앞 이벤트예flush 후 블록
XPeekEvent맨 앞 이벤트아니오flush 후 블록
XIfEventpredicate 함수예블록(블록할 때 flush)
XCheckIfEventpredicate 함수예False 반환(flush됨)
XPeekIfEventpredicate 함수아니오블록(블록할 때 flush)
XWindowEvent창 + 마스크예flush 후 블록
XCheckWindowEvent창 + 마스크예False 반환(flush됨)
XMaskEvent마스크예flush 후 블록
XCheckMaskEvent마스크예False 반환(flush됨)
XCheckTypedEvent이벤트 타입예False 반환(flush됨)
XCheckTypedWindowEvent타입 + 창예False 반환(flush됨)

이름에 Check가 붙은 함수는 블록하지 않고 Bool을 돌려준다. 골라 꺼내는 함수들은 맞지 않는 다른 이벤트를 버리지 않고 큐에 그대로 둔다. 그래서 "순서를 건너뛰어" 원하는 이벤트를 먼저 처리할 수 있다.

다음 이벤트 꺼내기

XNextEvent(Display *display, XEvent *event_return);

큐의 첫 이벤트를 event_return에 복사하고 큐에서 지운다. 큐가 비어 있으면 출력 버퍼를 비우고 이벤트가 올 때까지 기다린다. 이벤트 루프의 중심 함수다.

XPeekEvent(Display *display, XEvent *event_return);

큐의 첫 이벤트를 복사해 주되 지우지 않는다. 큐가 비면 flush 후 기다린다. "다음 이벤트가 무엇인지 보고 지금 처리를 결정"할 때 쓴다.

/* 키 자동 반복(auto-repeat) 걸러내기: Release 바로 뒤에 같은 시각의 Press가 오면 반복 */
case KeyRelease:
    if (XEventsQueued(dpy, QueuedAfterReading)) {
        XEvent nx;
        XPeekEvent(dpy, &nx);
        if (nx.type == KeyPress && nx.xkey.time == ev.xkey.time
            && nx.xkey.keycode == ev.xkey.keycode) {
            XNextEvent(dpy, &nx);      /* 반복으로 생긴 Press도 버림 */
            break;
        }
    }
    key_up(ev.xkey.keycode);
    break;

(XPeekEvent는 큐가 비면 블록하므로, 먼저 XEventsQueued로 이벤트가 있는지 확인했다.)

predicate 함수로 고르기

세 함수(XIfEvent, XCheckIfEvent, XPeekIfEvent)는 이벤트가 원하는 것인지 판정하는 함수(predicate)를 받는다. 형태는 다음과 같다.

Bool predicate(Display *display, XEvent *event, XPointer arg);
  • event: 검사할 이벤트.
  • arg: XIfEvent 등에 넘긴 사용자 인자 그대로(조건값을 넘기는 용도).

predicate는 큐의 이벤트마다 한 번씩, 맞는 것을 찾을 때까지 불린다. 맞으면 True, 아니면 False를 돌려준다.

중요한 제약: predicate 안에서 Xlib 함수를 부르면 안 된다. predicate가 직접이든 간접이든 이벤트 큐 상태를 바꾸면 결과는 정의되지 않는다. Xlib이 스레드용으로 초기화되어 있으면 predicate는 디스플레이가 잠긴 채 불리므로, 디스플레이를 잠그는 Xlib 함수를 부르면(먼저 XLockDisplay를 부르지 않은 한) 결과가 정의되지 않는다. 이벤트 필드만 보고 판단한다.
XIfEvent(Display *display, XEvent *event_return, Bool (*predicate)(), XPointer arg);

predicate가 True를 돌려주는 이벤트가 나올 때까지 기다린다. 기다리게 되면 flush한다. 맞는 이벤트를 큐에서 지우고 event_return에 복사한다.

Bool XCheckIfEvent(Display *display, XEvent *event_return, Bool (*predicate)(), XPointer arg);

블록하지 않는 판. 맞는 것이 있으면 복사·제거하고 True. 없으면 False를 돌려주며, 그때 출력 버퍼는 비워진 상태다. 앞서 쌓인 이벤트는 버리지 않는다.

XPeekIfEvent(Display *display, XEvent *event_return, Bool (*predicate)(), XPointer arg);

맞는 이벤트가 나올 때까지 기다려 복사하되, 큐에서 지우지 않는다. 기다리면 flush한다.

대표적인 사용 예: 창을 매핑한 뒤 실제로 매핑될 때까지 기다리기.

static Bool is_map_notify(Display *d, XEvent *e, XPointer arg) {
    return e->type == MapNotify && e->xmap.window == *(Window *)arg;
}
...
XSelectInput(dpy, win, StructureNotifyMask | ExposureMask);
XMapWindow(dpy, win);
XEvent ev;
XIfEvent(dpy, &ev, is_map_notify, (XPointer)&win);   /* MapNotify가 올 때까지 */
/* 이제 XSetInputFocus 등 매핑된 창이 필요한 요청을 보낼 수 있다 */

이렇게 하면 기다리는 동안 들어온 Expose 같은 다른 이벤트는 큐에 그대로 남아 나중에 루프에서 처리된다.

창이나 이벤트 마스크로 고르기

이 함수들은 창이나 이벤트 종류로 골라서, 순서를 바꿔 처리할 수 있게 해 준다.

XWindowEvent(Display *display, Window w, long event_mask, XEvent *event_return);

창 w와 event_mask 모두에 맞는 이벤트를 큐에서 찾아 지우고 복사한다. 다른 이벤트는 그대로 둔다. 없으면 flush 후 기다린다.

Bool XCheckWindowEvent(Display *display, Window w, long event_mask, XEvent *event_return);

블록하지 않는 판. 큐를 먼저 찾고, 그다음 서버 연결에서 읽을 수 있는 이벤트까지 찾는다. 있으면 True, 없으면 False(출력 버퍼는 비워짐).

XMaskEvent(Display *display, long event_mask, XEvent *event_return);

창과 상관없이 마스크에 맞는 이벤트를 찾아 지우고 복사한다. 없으면 flush 후 기다린다.

Bool XCheckMaskEvent(Display *display, long event_mask, XEvent *event_return);

블록하지 않는 판. 큐와 연결을 찾아 있으면 True, 없으면 False.

Bool XCheckTypedEvent(Display *display, int event_type, XEvent *event_return);

마스크가 아니라 이벤트 타입(Expose, MotionNotify 등)으로 찾는다. 큐와 연결을 찾아 첫 번째로 맞는 것을 꺼내고 True, 없으면 False.

Bool XCheckTypedWindowEvent(Display *display, Window w, int event_type, XEvent *event_return);

타입과 창이 모두 맞는 첫 이벤트를 꺼낸다. 없으면 False.

마스크 함수와 타입 함수의 차이: 마스크로는 고를 수 없는 이벤트가 있다. ClientMessage, SelectionNotify 같은 마스크 없는 이벤트는 XMaskEvent/XWindowEvent로 꺼낼 수 없으므로 XCheckTypedEvent나 predicate 함수를 쓴다. 또 MotionNotify처럼 여러 마스크가 한 타입에 대응하는 경우 타입 함수가 더 직관적이다.

실전 예 1: Expose 압축. 창 하나에 Expose가 여러 개 쌓였을 때 한 번만 다시 그린다.

case Expose: {
    XEvent extra;
    /* 같은 창의 남은 Expose를 모두 걷어 낸다 */
    while (XCheckTypedWindowEvent(dpy, ev.xexpose.window, Expose, &extra))
        ;
    redraw_all(ev.xexpose.window);
    break;
}

실전 예 2: 이동 이벤트 압축. 처리가 느릴 때 가장 최근 위치만 쓴다.

case MotionNotify: {
    XEvent latest = ev;
    while (XCheckTypedWindowEvent(dpy, ev.xmotion.window, MotionNotify, &latest))
        ;                                /* 마지막 것만 남긴다 */
    drag_to(latest.xmotion.x, latest.xmotion.y);
    break;
}

실전 예 3: Esc 키로 긴 작업 중단 확인(블록하지 않음).

for (int i = 0; i < big_job_steps; i++) {
    do_step(i);
    XEvent k;
    if (XCheckWindowEvent(dpy, win, KeyPressMask, &k) &&
        XLookupKeysym(&k.xkey, 0) == XK_Escape)   /* XK_Escape: <X11/keysym.h> */
        break;
}

11.5 이벤트를 큐에 되돌려 놓기

XPutBackEvent(Display *display, XEvent *event);

이벤트를 복사해서 큐의 맨 앞에 다시 넣는다. 이벤트를 읽었다가 "이건 나중에 처리하자"고 마음을 바꿨을 때 쓴다. 연속해서 몇 번이든 부를 수 있다. 맨 앞에 넣으므로 다음 XNextEvent가 바로 이 이벤트를 돌려준다. 여러 개를 되돌리면 마지막에 되돌린 것이 먼저 나온다.

XEvent ev;
XNextEvent(dpy, &ev);
if (ev.type == KeyPress && !ready_for_keys) {
    XPutBackEvent(dpy, &ev);   /* 다음 XNextEvent에서 다시 나온다 */
}
되돌린 이벤트를 곧바로 다시 꺼내 다시 되돌리는 루프를 만들면 무한 반복에 빠진다. 되돌린 뒤에는 다른 일을 하고 나서 다시 꺼내야 한다.

11.6 다른 프로그램에 이벤트 보내기

Status XSendEvent(Display *display, Window w, Bool propagate, long event_mask, XEvent *event_send);

지정한 창으로 이벤트를 보낸다. 셀렉션 처리에서 자주 쓴다. 예를 들어 셀렉션 소유자는 데이터를 변환해 프로퍼티에 저장한 뒤 XSendEvent로 요청자에게 SelectionNotify를 보내야 한다.

  • w: 받을 창. 특수값 PointerWindow(포인터가 들어 있는 창), InputFocus도 쓸 수 있다.
  • propagate: 받을 클라이언트가 없을 때 조상 창으로 전파할지.
  • event_mask: 받을 클라이언트를 고르는 마스크(10.3절).
  • event_send: 보낼 이벤트.

이 함수는 목적지 창을 정하고, 어느 클라이언트가 받을지 정하고, 걸려 있는 능동 그랩은 무시한다.

목적지 창 정하기

  • w가 PointerWindow: 포인터가 들어 있는 창.
  • w가 InputFocus: 포커스 창이 포인터를 담고 있으면 포인터가 들어 있는 창, 아니면 포커스 창.

받을 클라이언트 정하기

  1. event_mask가 비어 있으면(0): 목적지 창을 만든 클라이언트에게 보낸다. 그 클라이언트가 이미 없으면 아무에게도 안 간다.
  2. propagate가 False: 목적지 창에서 event_mask의 이벤트 종류 중 하나라도 고른 모든 클라이언트에게 보낸다.
  3. propagate가 True이고 목적지 창에서 그 종류를 고른 클라이언트가 없으면: 목적지를 "그 종류를 고른 클라이언트가 있고, 중간 창의 do-not-propagate-mask가 그 종류를 막지 않는" 가장 가까운 조상으로 바꾼다. 그런 창이 없거나, 처음에 InputFocus를 지정했는데 그 창이 포커스 창의 조상이면 아무에게도 보내지 않는다. 아니면 최종 목적지에서 그 종류를 고른 모든 클라이언트에게 보낸다.

이벤트는 코어 이벤트이거나 확장이 정의한 이벤트여야 한다(아니면 BadValue). 서버가 바이트 순서를 바꿔(byte-swap) 줄 수 있어야 하기 때문이다. 그 밖에 서버는 내용을 고치거나 검사하지 않는다. 다만 전달하는 이벤트의 send_event를 강제로 True로 바꾸고 serial을 올바르게 채운다. 그래서 이 두 필드와 display 필드는 XSendEvent가 무시한다.

반환값: 와이어 프로토콜 형식으로의 변환에 실패하면 0, 아니면 0이 아닌 값. BadValue, BadWindow 오류가 날 수 있다.

반환값이 0이 아니라고 해서 상대가 받았다는 뜻은 아니다. 변환이 됐다는 뜻일 뿐이다. 실제 전달 여부는 알 수 없다. 또 요청은 출력 버퍼에 쌓이므로 바로 가게 하려면 XFlush를 부른다.

예 1: 다른 스레드나 타이머에서 자기 이벤트 루프를 깨우기(자기 창에 ClientMessage 보내기). event_mask를 0으로 주면 창을 만든 클라이언트(자기 자신)에게 간다.

Atom wake = XInternAtom(dpy, "MY_APP_WAKEUP", False);
XEvent e;
memset(&e, 0, sizeof e);
e.xclient.type         = ClientMessage;
e.xclient.window       = win;
e.xclient.message_type = wake;
e.xclient.format       = 32;
e.xclient.data.l[0]    = 42;          /* 원하는 값 */
XSendEvent(dpy, win, False, 0, &e);
XFlush(dpy);

(여러 스레드에서 같은 Display를 쓰려면 프로그램 시작 때 XInitThreads를 불러야 한다. 이 장의 범위 밖이다.)

예 2: 창 관리자에게 요청 보내기(EWMH 규약). 루트 창으로 보내고, 창 관리자가 고른 마스크를 지정한다.

/* 창을 전체 화면으로 바꿔 달라고 요청 */
XEvent e;
memset(&e, 0, sizeof e);
e.xclient.type         = ClientMessage;
e.xclient.window       = win;
e.xclient.message_type = XInternAtom(dpy, "_NET_WM_STATE", False);
e.xclient.format       = 32;
e.xclient.data.l[0]    = 1;   /* _NET_WM_STATE_ADD */
e.xclient.data.l[1]    = XInternAtom(dpy, "_NET_WM_STATE_FULLSCREEN", False);
XSendEvent(dpy, DefaultRootWindow(dpy), False,
           SubstructureRedirectMask | SubstructureNotifyMask, &e);
받는 쪽에서는 send_event가 True인지 보고 합성 이벤트를 구분할 수 있다. 보안상 일부 프로그램(예: 터미널)은 XSendEvent로 온 가짜 KeyPress를 무시한다. 그래서 XSendEvent로 다른 앱에 키 입력을 흉내 내는 방법은 잘 통하지 않는다.

11.7 포인터 이동 기록 얻기

어떤 X 서버는 이벤트로 알려 주는 것보다 더 촘촘한 포인터 이동 기록을 가진다. 포인터 하드웨어 인터럽트마다 위치를 버퍼에 저장해 두는데, 이것을 모션 히스토리 버퍼라 한다. 그림 그리기 프로그램처럼 포인터가 지나간 길을 정확히 알아야 하는 앱 몇몇이 쓴다. 대부분의 앱에는 지나치게 많은 정보다. (자주 쓰지 않아 요약만)

unsigned long XDisplayMotionBufferSize(Display *display);

모션 버퍼가 담을 수 있는 대략의 최대 항목 수를 돌려준다.

XTimeCoord *XGetMotionEvents(Display *display, Window w, Time start, Time stop, int *nevents_return);

typedef struct {
	Time time;
	short x, y;
} XTimeCoord;

start~stop 시각(양 끝 포함) 사이에 있고, 좌표가 창 w(테두리 포함, 현재 위치 기준) 안에 드는 모든 기록을 돌려준다. 시각에는 타임스탬프나 CurrentTime을 줄 수 있다. 개수는 nevents_return에 들어간다. 서버가 모션 히스토리를 지원하지 않거나, start가 stop보다 늦거나, start가 미래면 아무것도 돌려주지 않고 NULL을 돌려준다. stop이 미래면 CurrentTime과 같다. time은 밀리초, x, y는 창 w 기준 좌표다. 결과는 XFree로 해제한다. BadWindow 오류가 날 수 있다.

int n;
XTimeCoord *tc = XGetMotionEvents(dpy, win, last_time, ev.xmotion.time, &n);
if (tc) {
    for (int i = 0; i < n; i++) add_point(tc[i].x, tc[i].y);
    XFree(tc);
}
last_time = ev.xmotion.time;

11.8 프로토콜 오류 처리

Xlib은 요청을 버퍼에 모아 비동기로 보낸다. 그래서 오류도 나중에 도착한다. 예를 들어 잘못된 창 ID로 XMoveWindow를 불러도 그 함수는 그냥 돌아오고, 몇 줄 뒤 Xlib이 서버에서 오류 메시지를 읽을 때 오류 처리기가 불린다. 이 절은 이 비동기성을 다루는 방법(동기 모드)과 오류 처리기를 바꾸는 방법을 다룬다.

동기 모드 켜고 끄기

디버깅할 때는 Xlib이 동기적으로 동작해 오류가 생긴 바로 그 자리에서 보고되게 하면 편하다. 대신 그래픽이 30배 이상 느려질 수 있다. POSIX 시스템에는 전역 변수 _Xdebug도 있는데, 디버거에서 프로그램을 시작하기 전에 0이 아닌 값으로 설정하면 동기 동작을 강제한다.

프로토콜 요청을 만드는 모든 Xlib 함수는 일을 마친 뒤 "after function"이라는 함수를 부른다. 이것을 정하는 함수가 XSetAfterFunction이다.

int (*XSetAfterFunction(Display *display, int (*procedure)()))();

procedure는 디스플레이 포인터 하나만 받고 불린다. 이전 after function을 돌려준다.

int (*XSynchronize(Display *display, Bool onoff))();

onoff가 True면 동기 동작을 켜고 False면 끈다. 이전 after function을 돌려준다. 내부적으로는 매 요청 뒤에 XSync를 부르는 after function을 설치하는 것과 같다.

#ifdef DEBUG
XSynchronize(dpy, True);   /* 오류가 난 함수에서 바로 처리기가 불린다 */
#endif
디버거에서 오류 위치를 찾는 법: XSynchronize(dpy, True)를 켜고 오류 처리기 안에 중단점을 걸면, 콜 스택에서 오류를 낸 Xlib 호출을 바로 볼 수 있다. 동기 모드가 꺼져 있으면 스택에는 엉뚱한 나중 호출이 보인다.

기본 오류 처리기 사용하기

Xlib에는 기본 오류 처리기가 두 개 있다. 하나는 치명적 상황(예: 기계가 죽어서 디스플레이 서버와의 연결이 끊김)을 위한 것이고, 다른 하나는 X 서버가 보낸 프로토콜 오류를 위한 것이다. 둘 다 원하는 함수로 언제든 몇 번이든 바꿀 수 있다. NULL을 넘기면 기본 처리기로 돌아간다. 기본 처리기는 설명 메시지를 출력하고 프로그램을 끝낸다(exit).

int (*XSetErrorHandler(int (*handler)(Display *, XErrorEvent *)))();

프로토콜 오류 처리기를 설정하고, 이전 처리기를 돌려준다.

  • Xlib은 오류를 받을 때마다 대체로 이 처리기를 부른다. 단 OpenFont, LookupColor, AllocNamedColor 요청의 BadName 오류와 QueryFont 요청의 BadFont 오류에는 부르지 않는다. 이런 오류는 함수의 반환값으로 프로그램에 알려진다(예: XLoadQueryFont가 NULL을 돌려줌).
  • 치명적인 상황으로 가정하지 않으므로 처리기가 그냥 return해도 된다. 반환값은 무시된다.
  • 처리기 안에서는 그 디스플레이에 프로토콜 요청을 만들거나 입력 이벤트를 찾는 함수를 (직접이든 간접이든) 부르면 안 된다. Xlib 내부가 오류를 처리하는 도중이기 때문이다.

처리기가 받는 XErrorEvent:

typedef struct {
	int type;
	Display *display;           /* 오류를 읽어 온 디스플레이 */
	unsigned long serial;       /* 실패한 요청의 일련번호 */
	unsigned char error_code;   /* 오류 코드 */
	unsigned char request_code; /* 실패한 요청의 major opcode */
	unsigned char minor_code;   /* 실패한 요청의 minor opcode */
	XID resourceid;             /* 관련 자원 ID */
} XErrorEvent;
  • serial: 연결을 연 뒤 보낸 요청 수(1부터). 실패한 호출 직전의 NextRequest(dpy) 값과 같다. 그래서 의심 가는 호출 전에 NextRequest를 기록해 두면 어떤 호출이 오류를 냈는지 맞춰 볼 수 있다.
  • request_code: 실패한 프로토콜 요청 번호(<X11/Xproto.h>의 X_CreateWindow 등).
  • error_code: 아래 표의 코드.
  • resourceid: 문제가 된 자원(창, GC 등)의 ID.

예: 오류 처리기로 BadWindow 잡기

다른 프로그램의 창을 다룰 때는 그 창이 언제 사라질지 모른다. 기본 처리기는 BadWindow를 받으면 프로그램을 끝내 버리므로, 위험한 구간만 처리기를 바꿔 오류를 "잡는" 방법을 흔히 쓴다.

/* cc trap.c -lX11 */
#include <X11/Xlib.h>
#include <stdio.h>

static int trapped_error = 0;

static int trap_handler(Display *dpy, XErrorEvent *e) {
    char msg[128];
    XGetErrorText(dpy, e->error_code, msg, sizeof msg);  /* 로컬 조회, 요청 안 만듦 */
    fprintf(stderr, "X error: %s (request %d, serial %lu, id 0x%lx)\n",
            msg, e->request_code, e->serial, e->resourceid);
    trapped_error = e->error_code;
    return 0;                      /* 반환값은 무시됨, 프로그램은 계속 */
}

/* 창이 이미 없어졌어도 죽지 않고 False를 돌려준다 */
Bool safe_get_attrs(Display *dpy, Window w, XWindowAttributes *wa) {
    int (*old)(Display *, XErrorEvent *);
    Status ok;

    XSync(dpy, False);             /* 앞서 쌓인 요청의 오류는 원래 처리기로 */
    trapped_error = 0;
    old = XSetErrorHandler(trap_handler);
    ok = XGetWindowAttributes(dpy, w, wa);
    XSync(dpy, False);             /* 이 구간의 오류가 지금 처리되게 함 */
    XSetErrorHandler(old);         /* 원래 처리기 복원 */
    return ok && trapped_error == 0;
}

핵심은 앞뒤의 XSync다. 오류는 비동기로 오므로, 처리기를 바꾸기 전에 XSync로 이전 요청의 오류를 모두 처리해 두고, 구간이 끝난 뒤에 다시 XSync로 이 구간의 오류가 바뀐 처리기에서 처리되도록 강제한다. 마지막 XSync를 빼면 오류가 처리기를 되돌린 뒤에 도착해 기본 처리기가 프로그램을 끝낼 수 있다.

함정: 처리기 안에서 XSync, XNextEvent, 창 그리기 같은 함수를 부르면 안 된다. 기록만 하고 돌아온 뒤 처리기 밖에서 대응한다. 또 XSetErrorHandler는 디스플레이별이 아니라 프로세스 전체에 하나다. 라이브러리 안에서 바꿨다면 반드시 이전 처리기로 되돌린다.

BadImplementation서버가 요청의 어떤 부분을 구현하지 않음. 코어 요청에서 이것을 내는 서버는 결함이 있는 것이지만, 클라이언트는 받을 준비를 해야 한다
BadLength요청 길이가 인자를 담기에 짧거나 김(Xlib이나 서버 내부 오류); 또는 요청 길이가 서버가 받는 최대 길이를 넘음
BadMatch그래픽 요청에서 GC의 루트·깊이가 drawable과 맞지 않음; InputOnly 창을 drawable로 씀; 인자의 타입·범위는 맞지만 요청이 요구하는 다른 조건에 맞지 않음; InputOnly 창에 없는 속성을 다룸
BadName지정한 이름의 폰트나 색이 없음
BadPixmap픽스맵 인자가 정의된 픽스맵이 아님
BadRequestmajor/minor opcode가 올바른 요청이 아님. 보통 Xlib이나 서버 오류
BadValue숫자 값이 요청이 받는 범위를 벗어남. 범위가 따로 정해지지 않은 인자는 그 타입의 전체 범위를 받는다. 여러 선택지 중 하나를 고르는 인자는 대개 이 오류를 낼 수 있다
BadWindow창 인자가 정의된 창이 아님

BadAtom, BadColor, BadCursor, BadDrawable, BadFont, BadGC, BadPixmap, BadWindow는 인자 타입이 고정된 특수값(예: None, ParentRelative)으로 확장된 경우에도 쓰인다.

오류 메시지 문자열 얻기

XGetErrorText(Display *display, int code, char *buffer_return, int length);

오류 코드 code를 설명하는 널 종료 문자열을 buffer_return(크기 length)에 복사한다. 텍스트는 현재 로캘의 인코딩이다. 확장이 자기 오류 코드와 문자열을 정의할 수 있으므로, 직접 표를 만들지 말고 이 함수를 쓰는 것이 권장된다.

XGetErrorDatabaseText(Display *display, char *name, char *message, char *default_string, char *buffer_return, int length);

오류 메시지 데이터베이스에서 메시지를 찾아(없으면 default_string) 널 종료 문자열로 돌려준다. Xlib이 내부적으로 자기 오류 메시지를 찾을 때 쓴다. default_string과 결과 모두 현재 로캘 인코딩이다.

  • name: 보통 앱 이름. message: 원하는 메시지 종류. 둘이 Host Portable Character Encoding이 아니면 결과는 구현에 따라 다르다.
  • Xlib이 쓰는 미리 정의된 "앱 이름" 세 개(대소문자 구분):
    • XProtoError: 프로토콜 오류 번호를 문자열로 만들어 message로 쓴다.
    • XlibMessage: 라이브러리 내부 메시지 문자열.
    • XRequest: 코어 요청은 major 요청 번호를, 확장 요청은 "확장 이름(InitExtension에 준 것).minor 번호"를 message로 쓴다.

요청 번호를 사람이 읽는 이름으로 바꾸는 예:

char num[16], reqname[64];
snprintf(num, sizeof num, "%d", e->request_code);
XGetErrorDatabaseText(dpy, "XRequest", num, "unknown", reqname, sizeof reqname);
fprintf(stderr, "failed request: %s\n", reqname);   /* 예: "X_GetWindowAttributes" */

디스플레이 이름 보고

char *XDisplayName(char *string);

XOpenDisplay가 쓰려고 할 디스플레이 이름을 돌려준다. NULL을 주면 환경 변수(DISPLAY)에서 찾아 그 이름을 돌려준다. 연결에 실패했을 때 사용자에게 정확히 어느 디스플레이를 열려 했는지 알려 주는 데 쓴다(11장 첫 예제 참고).

치명적 I/O 오류 처리기

int (*XSetIOErrorHandler(int (*handler)(Display *)))(Display *);

치명적 I/O 오류 처리기를 설정하고 이전 처리기를 돌려준다. 서버와의 연결이 끊기는 등 시스템 호출 오류가 생기면 불린다. 치명적 상황으로 가정하므로 처리기는 return하지 않아야 한다. return하면 클라이언트 프로세스가 끝난다(exit).

static int on_io_error(Display *dpy) {
    (void)dpy;
    fprintf(stderr, "X 서버 연결이 끊겼다. 작업을 저장하고 끝낸다.\n");
    save_user_work();      /* X 함수가 아닌 정리만 한다 */
    exit(1);               /* 어차피 return하면 Xlib이 exit한다 */
}
...
XSetIOErrorHandler(on_io_error);
I/O 오류 처리기 안에서는 연결이 이미 죽었으므로 그 디스플레이에 Xlib 함수를 쓰지 않는다. 파일 저장 같은 X와 무관한 정리만 하고 끝낸다. "X 서버가 죽어도 앱이 살아남게" 하려면 longjmp 같은 위험한 방법이 필요한데, Xlib 내부 상태가 깨진 채 남으므로 그 Display를 다시 쓸 수 없다.
