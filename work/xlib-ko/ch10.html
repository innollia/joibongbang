10장. 이벤트 (Events)

클라이언트는 XOpenDisplay로 연 연결 하나로 X 서버와 이야기한다. 클라이언트가 Xlib 함수를 부르면 그 함수가 요청(request)을 만들어 이 연결로 보낸다. 반대 방향으로는 서버가 이벤트를 보낸다. 이벤트는 두 가지 이유로 생긴다. 하나는 사용자가 키를 누르거나 마우스를 움직이는 것처럼 장치에서 일이 생길 때이고, 다른 하나는 클라이언트가 보낸 요청의 부수 효과(예: 창을 매핑하면 MapNotify, 창이 드러나면 Expose)다. 이벤트는 요청과 같은 연결로, 언제든 비동기적으로 도착한다.

이 장은 이벤트의 종류, 구조체, 마스크, 그리고 서버가 각 이벤트를 언제 어떻게 만드는지를 다룬다. 이벤트를 실제로 꺼내 쓰는 함수(XNextEvent 등)는 11장에서 다룬다.

10.1 이벤트 타입

이벤트는 X 서버가 비동기적으로 만들어 내는 데이터다. X의 기본 원칙은 "물어본 것만 알려 준다"이다. 서버는 클라이언트가 어떤 창에 대해 그 종류의 이벤트를 원한다고 등록했을 때만 그 이벤트를 보낸다. 등록은 보통 창의 event-mask 속성을 설정해서 한다. 창을 만들 때 정해도 되고, 나중에 바꿔도 된다.

왜 이렇게 할까? X는 네트워크 너머에서도 동작하도록 설계되었다. 마우스를 움직일 때마다 모든 클라이언트에게 이벤트를 쏟아부으면 네트워크와 클라이언트가 감당하지 못한다. 그래서 필요한 것만 골라 받게 한다.

키보드·마우스처럼 장치에서 생긴 이벤트는 원래 생긴 창(source window)에서 시작해 부모 쪽으로 올라가며(전파, propagation) 그 이벤트를 원하는 클라이언트가 있는 창을 찾는다. 창 속성의 do-not-propagate 마스크로 이 전파를 막을 수도 있다. 예외로 MappingNotify는 등록 여부와 상관없이 항상 모든 클라이언트에게 간다.

각 이벤트 타입마다 <X11/X.h>에 상수 이름이 정의되어 있다. 분류는 다음과 같다.

10.2 이벤트 구조체

이벤트 타입마다 대응하는 구조체가 <X11/Xlib.h>에 선언되어 있다. 모든 이벤트 구조체는 앞부분이 똑같다. 이 공통 부분만 떼어 놓은 것이 XAnyEvent다.

typedef struct {
     int           type;
     unsigned long serial;     /* 서버가 마지막으로 처리한 요청 번호 */
     Bool          send_event; /* SendEvent 요청으로 온 것이면 True */
     Display       *display;   /* 이벤트를 읽어 온 디스플레이 */
     Window        window;
} XAnyEvent;
  • type: 이벤트 종류 상수(예: GraphicsExpose). 이 값을 보고 어떤 구조체로 읽을지 정한다.
  • serial: 이 이벤트가 생길 때 서버가 마지막으로 처리한 요청의 일련번호. 프로토콜에서는 하위 16비트만 오지만 Xlib이 전체 32비트 값으로 늘려 준다. 어떤 요청 이후에 생긴 이벤트인지 가릴 때 쓴다.
  • send_event: 서버가 스스로 만든 것이 아니라 다른 클라이언트가 XSendEvent로 보낸 것이면 True. 진짜 키 입력인지 가짜인지 구분할 수 있다.
  • display: 이벤트를 읽어 온 디스플레이 포인터.
  • window: 툴킷의 디스패처(창별로 처리 함수를 찾아 부르는 코드)에 가장 쓸모 있는 창. 이벤트마다 의미가 조금 다르다.

서버는 입력 스트림 어디에든 이벤트를 끼워 보낼 수 있다. 그래서 Xlib이 어떤 요청의 응답(reply)을 기다리는 동안 이벤트가 먼저 도착하면, Xlib은 그 이벤트를 버리지 않고 이벤트 큐에 쌓아 둔다. 나중에 11장의 함수로 큐에서 꺼낸다.

개별 구조체 외에, 모든 이벤트 구조체를 하나로 묶은 공용체(union) XEvent가 있다.

     int                            type;          /* 바꾸면 안 됨 */

왜 공용체인가? 이벤트를 받는 쪽은 무슨 이벤트가 올지 미리 모른다. 그래서 가장 큰 이벤트도 담을 수 있는 그릇 하나(XEvent)를 준비해 받고, type을 본 뒤 알맞은 멤버(xkey, xbutton 등)로 읽는다. 공용체이므로 모든 멤버가 같은 메모리를 공유한다. 첫 5개 필드(type, serial, send_event, display, window)의 순서는 모든 구조체에서 같고, 툴킷이 깨지지 않도록 앞으로도 바뀌지 않는다. 그래서 어떤 이벤트든 ev.xany.window로 창을 읽을 수 있다(단, KeymapNotify의 window는 쓰이지 않는다). pad[24]는 확장 이벤트를 담을 여유 공간이다. 대부분의 이벤트에는 사건이 일어난 시각인 time 멤버도 있다.

XEvent ev;
XNextEvent(dpy, &ev);
switch (ev.type) {
case KeyPress:
    printf("keycode=%u state=0x%x\n", ev.xkey.keycode, ev.xkey.state);
    break;
case ButtonPress:
    printf("button %u at (%d,%d)\n", ev.xbutton.button, ev.xbutton.x, ev.xbutton.y);
    break;
case Expose:
    if (ev.xexpose.count == 0) redraw(ev.xexpose.window);
    break;
}
함정: type을 확인하지 않고 엉뚱한 멤버를 읽으면 컴파일은 되지만 쓰레기 값을 얻는다. 또 XEvent 대신 작은 구조체(예: XKeyEvent) 변수에 XNextEvent로 받으면 더 큰 이벤트가 올 때 메모리가 넘친다. 받을 때는 항상 XEvent를 쓴다. 특정 구조체 포인터가 필요하면 XKeyEvent *k = &ev.xkey;처럼 공용체 멤버의 주소를 쓴다(원문 표현으로는 "일반 이벤트 포인터는 캐스트한 뒤에 다른 정보에 접근해야 한다").

10.3 이벤트 마스크

대부분의 이벤트는 "어느 창에 대해" 받을지를 정해 등록한다. event_mask 인자를 받는 함수(XSelectInput, XCreateWindow의 속성 등)에 마스크를 넘긴다. 마스크의 비트는 <X11/X.h>에 정의되어 있고, 여러 개를 |로 묶는다.

등록하지 않으면 대부분의 이벤트는 생겨도 보고되지 않는다. 다만 몇 가지 예외가 있다.

  • GraphicsExpose와 NoExpose는 마스크가 아니라 GC의 graphics-exposures 값으로 정해진다. 기본값이 켜져 있으므로 XCopyArea/XCopyPlane을 쓰면 기본으로 온다. 원하지 않으면 GC에서 False로 끈다.
  • SelectionClear, SelectionRequest, SelectionNotify, ClientMessage는 마스크로 끌 수 없다. 셀렉션 관련 이벤트는 셀렉션에 참여하는 클라이언트에게만 간다.
  • 키보드·포인터 매핑이 바뀌면 MappingNotify가 항상 모두에게 간다.

10.4 이벤트 처리 개요

마스크와 이벤트 타입의 관계는 세 가지 경우가 있다.

  • 일대일: ButtonPressMask를 주면 ButtonPress만 온다.
  • 하나의 마스크가 여러 타입: SubstructureNotifyMask를 주면 CirculateNotify, ConfigureNotify, CreateNotify, DestroyNotify, GravityNotify, MapNotify, ReparentNotify, UnmapNotify가 올 수 있다.
  • 여러 마스크가 하나의 타입: PointerMotionMask든 ButtonMotionMask든 오는 것은 MotionNotify다.

이벤트 전파(propagation) 정리

키보드·포인터 계열(KeyPress, KeyRelease, ButtonPress, ButtonRelease, MotionNotify) 이벤트가 어느 창으로 보고되는지는 다음 규칙으로 정해진다(10.5절 원문 내용을 모아 정리).

  1. 이벤트의 원천(source)은 포인터가 들어 있는, 보이는(viewable) 가장 안쪽 창이다.
  2. 서버는 원천 창부터 위(부모, 조부모...)로 올라가며, 어떤 클라이언트든 그 이벤트 종류를 등록한 첫 번째 창을 찾는다. 그 창이 "이벤트 창"이 되고, 이벤트 구조체의 window에 들어간다.
  3. 올라가는 길에 있는 창의 do-not-propagate 마스크에 그 종류가 들어 있으면 거기서 이벤트가 사라진다.
  4. 능동 그랩(active grab)이 걸려 있으면 그랩한 클라이언트·창으로 보고된다. 키보드 이벤트는 포커스 창의 영향도 받는다.

원천 창이 이벤트 창의 자손이면, subwindow에 "이벤트 창의 자식 가운데 원천 창이거나 원천 창의 조상인 것"이 들어간다. 그래서 부모 창 하나만 등록해 두고도 subwindow를 보고 어느 자식 위에서 클릭했는지 알 수 있다.

/* 자식 창이 클릭을 받지 않게 하고 부모에서 한꺼번에 처리 */
XSetWindowAttributes a;
a.do_not_propagate_mask = 0;          /* 자식은 아무것도 막지 않음 */
a.event_mask = 0;                     /* 자식은 ButtonPress를 등록하지 않음 */
XChangeWindowAttributes(dpy, child, CWEventMask | CWDontPropagate, &a);
XSelectInput(dpy, parent, ButtonPressMask);
/* parent에서 받은 ev.xbutton.subwindow == child 이면 child 위의 클릭 */
전파는 장치 이벤트(키·버튼·이동)에만 해당한다. Expose, ConfigureNotify 같은 이벤트는 위로 올라가지 않는다. 부모에서 자식의 구조 변화를 보려면 SubstructureNotifyMask를 따로 건다.

cursorNone

이 자동 그랩은 모든 버튼이 (논리적으로) 떼어지면 저절로 끝난다. XUngrabPointer나 XChangeActivePointerGrab으로 도중에 바꿀 수 있다.

왜 이런 장치가 있을까? 버튼을 누른 채 창 밖으로 드래그해도 누른 창이 ButtonRelease와 이동 이벤트를 계속 받게 하려는 것이다. 버튼을 누른 창이 떼는 것도 확실히 알아야 버튼 "눌림" 표시를 되돌릴 수 있다.

ButtonPressMask는 한 창에 한 클라이언트만 등록할 수 있다(11장 참고). 자동 그랩이 누구 것인지 하나로 정해져야 하기 때문이다.

키·버튼·이동 이벤트

서버는 키나 버튼의 상태가 논리적으로 바뀌면 KeyPress/KeyRelease, ButtonPress/ButtonRelease를 보고한다. 키 이벤트는 Shift·Ctrl 같은 모디파이어 키에도 생긴다. 포인터가 논리적으로 움직이면 MotionNotify를 보고하는데, 이동이 한 창 안에서 시작하고 끝날 때만 생긴다(창을 넘나드는 것은 Enter/Leave가 맡는다). 이동 이벤트의 촘촘함은 보장되지 않지만, 포인터가 움직였다가 멈추면 적어도 하나는 받는 것이 보장된다. 그랩 때문에 장치 이벤트 처리가 얼어(frozen) 있으면 논리적 변화는 물리적 변화보다 늦게 생긴다.

받으려면 창의 event-mask에 KeyPressMask, KeyReleaseMask, ButtonPressMask, ButtonReleaseMask를 켠다. MotionNotify는 다음 중 하나 이상을 켠다.

  • Button1MotionMask~Button5MotionMask: 지정한 버튼 중 하나 이상이 눌린 동안만.
  • ButtonMotionMask: 아무 버튼이나 하나 이상 눌린 동안만(드래그).
  • PointerMotionMask: 버튼 상태와 상관없이 항상.
  • PointerMotionHintMask: 위 마스크와 함께 쓰면, 서버는 이벤트 창에 대해 is_hint가 NotifyHint인 MotionNotify 하나만 보내고, 키·버튼 상태가 바뀌거나 포인터가 창을 떠나거나 클라이언트가 XQueryPointer나 XGetMotionEvents를 부를 때까지 더 보내지 않아도 된다. 그래도 서버는 힌트가 아닌 일반 MotionNotify를 보낼 수도 있다.

힌트 모드는 "움직였다는 사실만 알려 주고, 정확한 위치는 네가 물어봐"라는 방식이다. 처리가 느린 클라이언트에 이동 이벤트가 수백 개 쌓이는 것을 막는다.

/* PointerMotionHintMask 사용 예 */
XSelectInput(dpy, win, ButtonMotionMask | PointerMotionHintMask | ButtonPressMask);
...
case MotionNotify:
    if (ev.xmotion.is_hint == NotifyHint) {
        Window r, c; int rx, ry, x, y; unsigned int m;
        /* 현재 위치를 묻는 동시에 다음 힌트를 다시 받을 수 있게 됨 */
        XQueryPointer(dpy, win, &r, &c, &rx, &ry, &x, &y, &m);
        draw_to(x, y);
    } else {
        draw_to(ev.xmotion.x, ev.xmotion.y);
    }
    break;

구조체는 다음과 같다. 셋은 거의 같고 마지막 "detail" 멤버만 다르다.

typedef struct {
     int            type;            /* ButtonPress 또는 ButtonRelease */
     unsigned long  serial;
     Bool           send_event;
     Display        *display;
     Window         window;          /* 보고 기준이 되는 "이벤트" 창 */
     Window         root;            /* 이벤트가 일어난 루트 창 */
     Window         subwindow;       /* 자식 창 */
     Time           time;            /* 밀리초 */
     int            x, y;            /* 이벤트 창 기준 포인터 좌표 */
     int            x_root, y_root;  /* 루트 기준 좌표 */
     unsigned int   state;           /* 키·버튼 마스크 */

     Bool           same_screen;
} XButtonEvent;
typedef XButtonEvent XButtonPressedEvent;
typedef XButtonEvent XButtonReleasedEvent;

typedef struct {
     int            type;            /* KeyPress 또는 KeyRelease */
     ... /* serial ~ state 까지 XButtonEvent와 같음 */
     unsigned int   keycode;         /* detail */
     Bool           same_screen;
} XKeyEvent;
typedef XKeyEvent XKeyPressedEvent;
typedef XKeyEvent XKeyReleasedEvent;

typedef struct {
     int            type;            /* MotionNotify */
     ... /* serial ~ state 까지 같음 */
     char           is_hint;         /* detail */
     Bool           same_screen;
} XMotionEvent;
typedef XMotionEvent XPointerMovedEvent;
  • window: 이벤트 창(위 전파 규칙으로 정해진 창).
  • root: 원천 창의 루트 창. x_root, y_root는 그 루트 기준 포인터 좌표.
  • same_screen: 이벤트 창이 루트 창과 같은 화면에 있으면 True. False면 x, y는 0이다.
  • subwindow: 원천 창이 이벤트 창의 자손이면 그 경로에 있는 이벤트 창의 자식, 아니면 None.
  • time: 이벤트가 생긴 서버 시각(밀리초). 더블클릭 판정이나 그랩·셀렉션 함수의 time 인자로 쓴다.
  • state: 이벤트 직전의 버튼·모디파이어 상태. Button1Mask~Button5Mask, ShiftMask, LockMask, ControlMask, Mod1Mask~Mod5Mask의 OR.
  • keycode: 물리 키를 나타내는 번호. 어느 글자인지는 키 매핑에 달려 있다(12.7절, 16.1절, 그리고 XLookupString 같은 함수로 변환).
  • button: 상태가 바뀐 버튼 Button1~Button5.
  • is_hint: NotifyNormal 또는 NotifyHint.
함정: state는 "직전" 상태다. 그래서 ButtonPress 이벤트의 state에는 방금 누른 버튼이 들어 있지 않고, ButtonRelease의 state에는 방금 뗀 버튼이 아직 들어 있다. 또 keycode는 글자가 아니다. 'a' 키인지 알려면 keysym으로 변환해야 한다.

case ButtonPress:

10.6 창 진입/이탈 이벤트

포인터 이동이나 창 계층 변화(창이 매핑·이동되어 포인터 밑에 다른 창이 오는 경우) 때문에 포인터가 이전과 다른 창에 있게 되면, 서버는 EnterNotify/LeaveNotify를 등록한 클라이언트에게 보낸다. 계층 변화로 생긴 Enter/Leave는 그 변화가 만든 계층 이벤트(UnmapNotify, MapNotify, ConfigureNotify, GravityNotify, CirculateNotify)보다 뒤에 온다. 하지만 FocusOut, VisibilityNotify, Expose와의 순서는 정해져 있지 않다. XGrabPointer/XUngrabPointer를 부를 때도 생길 수 있다.

받으려면 EnterWindowMask, LeaveWindowMask를 켠다.

typedef struct {
     int           type;           /* EnterNotify 또는 LeaveNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;         /* 이벤트 창 */
     Window        root;
     Window        subwindow;
     Time          time;
     int           x, y;
     int           x_root, y_root;
     int           mode;           /* NotifyNormal, NotifyGrab, NotifyUngrab */
     int           detail;         /* NotifyAncestor, NotifyVirtual, NotifyInferior,
                                      NotifyNonlinear, NotifyNonlinearVirtual */
     Bool          same_screen;
     Bool          focus;          /* 이벤트 창이 포커스 창(또는 그 자손)인가 */
     unsigned int  state;
} XCrossingEvent;
typedef XCrossingEvent XEnterWindowEvent;
typedef XCrossingEvent XLeaveWindowEvent;
  • subwindow: LeaveNotify면 처음 포인터 위치를 담은 자식, EnterNotify면 최종 포인터 위치를 담은 자식(없으면 None).
  • x, y: 항상 포인터의 최종 위치(이동 전 위치가 아님). 같은 화면이 아니면 0.
  • focus: 이벤트 창이 포커스 창이거나 그 자손이면 True.
  • state: 직전의 버튼·모디파이어 상태.
  • mode: 보통 이동이면 NotifyNormal, 그랩이 시작될 때의 가짜 이동이면 NotifyGrab, 그랩이 끝날 때면 NotifyUngrab.
  • detail: 창 계층에서 어떤 관계로 이동했는지.

보통(Normal) 진입/이탈

포인터가 창 A에서 창 B로 갈 때, 서버는 A와 B 사이의 모든 창에 이벤트를 만든다. "중간에 지나간" 창이 NotifyVirtual 계열을 받는다. 그래서 중첩된 창 각각이 "내 영역 안에 포인터가 있다"는 상태를 정확히 추적할 수 있다.

상황A(떠난 창)사이의 창들(양 끝 제외)B(들어간 창)
A가 B의 자손(안에서 바깥으로)LeaveNotify, NotifyAncestorLeaveNotify, NotifyVirtualEnterNotify, NotifyInferior
B가 A의 자손(바깥에서 안으로)LeaveNotify, NotifyInferiorEnterNotify, NotifyVirtualEnterNotify, NotifyAncestor
공통 조상 C를 사이에 둔 형제·사촌 관계LeaveNotify, NotifyNonlinearA~C 사이: LeaveNotify, C~B 사이: EnterNotify, 모두 NotifyNonlinearVirtualEnterNotify, NotifyNonlinear
다른 화면LeaveNotify, NotifyNonlinearA 위로 루트까지(루트 포함) LeaveNotify; B의 루트부터 B 직전까지 EnterNotify; 모두 NotifyNonlinearVirtualEnterNotify, NotifyNonlinear

detail 이름은 "상대 창이 나에게 무엇인가"로 읽으면 쉽다. A가 B의 자손일 때 A가 받는 Leave의 detail이 NotifyAncestor인 것은 "조상 쪽으로 나갔다"는 뜻이다. B가 받는 Enter가 NotifyInferior인 것은 "자손 쪽에서 들어왔다"는 뜻이다.

자주 하는 실수: 부모 창의 버튼을 하이라이트할 때 Leave를 받으면 무조건 하이라이트를 끈다. 그런데 포인터가 자식 창으로 들어가도 부모는 LeaveNotify(detail=NotifyInferior)를 받는다. 포인터는 여전히 부모 영역 안이다. "정말 나갔는지"를 보려면 detail != NotifyInferior를 확인한다.

그랩/언그랩 진입/이탈

포인터 그랩이 시작되거나 끝날 때 "가짜 이동" Enter/Leave가 생긴다. 그랩 창을 G, 포인터가 있는 창을 P라 하자.

  • 그랩 시작(confine_to 창으로의 초기 워프 뒤, 그랩을 일으킨 실제 ButtonPress를 만들기 전): 포인터가 P에서 G의 어딘가로 순간 이동한 것처럼 위 규칙대로 이벤트를 만들고 mode를 NotifyGrab으로 한다. 실제로는 포인터가 움직이지 않으므로 처음·나중 위치 모두 현재 위치다.
  • 그랩 끝(그랩을 끝낸 실제 ButtonRelease를 만든 뒤): G에서 P로 순간 이동한 것처럼 만들고 mode를 NotifyUngrab으로 한다.

그랩 중에는 다른 창이 이벤트를 받지 못하므로, 이 가짜 이벤트로 "이제 포인터가 너에게 없다고 생각해라"를 알려 주는 것이다.

10.7 입력 포커스 이벤트

키보드는 언제나 어떤 창(보통 루트 창이나 최상위 창)에 붙어 있다. 이것을 포커스 창이라 한다. 키 입력이 어느 창으로 갈지는 포커스 창과 포인터 위치가 함께 정한다. 포커스가 바뀐 것을 알면 텍스트 커서를 깜빡이거나 테두리를 강조하는 등 화면 표시를 바꿀 수 있다. FocusChangeMask를 켜면 FocusIn/FocusOut을 받는다.

typedef struct {
     int           type;       /* FocusIn 또는 FocusOut */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;     /* 이벤트가 생긴 창 */
     int           mode;       /* NotifyNormal, NotifyWhileGrabbed, NotifyGrab, NotifyUngrab */
     int           detail;     /* NotifyAncestor, NotifyVirtual, NotifyInferior,
                                  NotifyNonlinear, NotifyNonlinearVirtual, NotifyPointer,
                                  NotifyPointerRoot, NotifyDetailNone */
} XFocusChangeEvent;
typedef XFocusChangeEvent XFocusInEvent;
typedef XFocusChangeEvent XFocusOutEvent;

mode는 보통 포커스 변화(NotifyNormal), 그랩 중의 포커스 변화(NotifyWhileGrabbed), 키보드 그랩 시작(NotifyGrab), 끝(NotifyUngrab) 중 하나다. 창 언매핑으로 생긴 FocusOut은 UnmapNotify 뒤에 오지만, Enter/Leave/Visibility/Expose와의 순서는 정해져 있지 않다.

보통 포커스 이벤트와 그랩 중 포커스 이벤트

규칙은 Enter/Leave와 같은 모양(A·B와 그 사이 창에 Ancestor/Virtual/Inferior/Nonlinear/NonlinearVirtual)이다. 다른 점은 포인터 위치 P가 끼어든다는 것이다. 포커스가 창 B에 있고 포인터가 B 안쪽 자손 P에 있으면, 키 입력은 사실상 P 쪽으로 간다(포커스 창 안에서는 포인터 밑 창이 키를 받는다). 그래서 B부터 P까지의 창에 detail이 NotifyPointer인 이벤트가 추가로 생긴다.

포커스 이동생기는 이벤트(순서대로)
A → B, A가 B의 자손A: Out/NotifyAncestor; 사이: Out/NotifyVirtual; B: In/NotifyInferior; P가 B의 자손이면서 A나 A의 자손·조상이 아니면 B 아래~P(포함): In/NotifyPointer
A → B, B가 A의 자손P가 A의 자손이면서 B의 자손·조상이 아니면 P~A 직전: Out/NotifyPointer; A: Out/NotifyInferior; 사이: In/NotifyVirtual; B: In/NotifyAncestor
A → B, 공통 조상 CP가 A의 자손이면 P~A 직전: Out/NotifyPointer; A: Out/NotifyNonlinear; A~C 사이: Out/NotifyNonlinearVirtual; C~B 사이: In/NotifyNonlinearVirtual; B: In/NotifyNonlinear; P가 B의 자손이면 B 아래~P: In/NotifyPointer
A → B, 다른 화면위와 같되, 사이 창 대신 A 위로 루트까지(포함) Out/NotifyNonlinearVirtual, B의 루트부터 B 직전까지 In/NotifyNonlinearVirtual
A → PointerRoot 또는 NoneP가 A의 자손이면 P~A 직전: Out/NotifyPointer; A: Out/NotifyNonlinear; A 위로 루트까지: Out/NotifyNonlinearVirtual; 모든 화면의 루트: In/NotifyPointerRoot(또는 NotifyDetailNone); 새 포커스가 PointerRoot면 P의 루트~P(포함): In/NotifyPointer
PointerRoot 또는 None → A옛 포커스가 PointerRoot면 P~P의 루트(포함): Out/NotifyPointer; 모든 루트: Out/NotifyPointerRoot(또는 NotifyDetailNone); A가 루트가 아니면 A의 루트~A 직전: In/NotifyNonlinearVirtual; A: In/NotifyNonlinear; P가 A의 자손이면 A 아래~P: In/NotifyPointer
PointerRoot ↔ None옛 포커스가 PointerRoot면 P~P의 루트: Out/NotifyPointer; 모든 루트: Out/(NotifyPointerRoot 또는 NotifyDetailNone); 모든 루트: In/(NotifyDetailNone 또는 NotifyPointerRoot); 새 포커스가 PointerRoot면 P의 루트~P: In/NotifyPointer

PointerRoot는 "포인터 밑의 창으로 키를 보내라", None은 "키 입력을 버려라"라는 특수 포커스 값이다.

실용적으로는 대부분의 앱이 detail을 세세히 볼 필요가 없다. 최상위 창이 포커스를 얻었는지만 알고 싶다면 NotifyPointer와 NotifyVirtual/NotifyNonlinearVirtual(지나가는 창이 받는 것)를 무시하고, 나머지 FocusIn/FocusOut만으로 상태를 바꾸면 된다.

그랩이 만드는 포커스 이벤트

키보드 그랩(XGrabKeyboard)이 시작될 때(그랩을 일으킨 실제 KeyPress를 만들기 전), 그랩 창을 G, 현재 포커스를 F라 하면 포커스가 F에서 G로 바뀐 것처럼 FocusIn/FocusOut을 mode=NotifyGrab으로 만든다. 그랩이 끝날 때(그랩을 끝낸 실제 KeyRelease를 만든 뒤)는 G에서 F로 바뀐 것처럼 mode=NotifyUngrab으로 만든다.

10.8 키맵 상태 알림 이벤트

KeymapStateMask를 켜면, 서버는 EnterNotify와 FocusIn 바로 뒤에 매번 KeymapNotify를 보낸다. 창이 포커스를 얻은 순간 "지금 어떤 키가 이미 눌려 있는지"를 알려 주는 것이다. 예를 들어 Shift를 누른 채 창에 들어오면 그 창은 Shift의 KeyPress를 받은 적이 없는데, 이 이벤트로 상태를 맞출 수 있다.

typedef struct {
     int            type;           /* KeymapNotify */
     unsigned long  serial;
     Bool           send_event;
     Display        *display;
     Window         window;         /* 쓰이지 않음(툴킷 편의용) */
     char           key_vector[32];
} XKeymapEvent;

key_vector는 32바이트(256비트) 비트 벡터다. 바이트 N(0부터)은 키코드 8N~8N+7을 담고, 바이트의 최하위 비트가 키 8N이다. 비트가 1이면 그 키가 눌려 있다.

int key_down(const XKeymapEvent *e, unsigned int keycode) {
    return (e->key_vector[keycode / 8] >> (keycode % 8)) & 1;
}

10.9 노출(Exposure) 이벤트

X 프로토콜은 창이 가려지거나 재배치될 때 창 내용을 보존해 준다고 약속하지 않는다. 어떤 구현은 보존하고(backing store 등), 어떤 구현은 가려진 부분을 그냥 버린다. 그래서 X는 창 내용을 다시 그리는 책임을 클라이언트에게 맡긴다. 가려졌던 부분이 다시 보이게 되면(노출되면) 서버가 Expose 이벤트로 "이 창의 이 사각형이 비었으니 다시 그려라"라고 알려 준다. 단순한 앱은 창 전체를 다시 그리고, 신경 쓴 앱은 노출된 영역만 다시 그린다.

왜 이렇게 설계했을까? 화면 밖에 모든 창의 픽셀을 저장하려면 메모리가 많이 든다. X가 처음 나온 시절에는 이것이 큰 부담이었고, 원격 클라이언트가 그림 명령을 다시 보내는 편이 더 쌌다.

Expose 이벤트

Expose가 생기는 조건은 다른 이벤트만큼 명확하지 않다. 그래도 InputOnly 창에는 절대 생기지 않는다. 창의 어떤 영역에 유효한 내용이 없고, 그 영역이 보이거나, 보일 수 있는 상태에서 서버가 (새로) backing store를 유지하거나, 창이 보이지 않지만 서버가 backing-store 속성 Always/WhenMapped를 (새로) 지키게 될 때 생길 수 있다. 영역은 임의의 사각형 집합으로 나뉘고, 사각형마다 Expose 하나가 생긴다. 창을 올리는 것 같은 한 동작이 만든 노출 영역은 연속해서(중간에 다른 것 없이) 보고된다.

ExposureMask를 켜면 받는다.

typedef struct {
     int           type;           /* Expose */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;         /* 노출된(손상된) 창 */
     int           x, y;           /* 사각형 왼쪽 위(창 기준) */
     int           width, height;  /* 사각형 크기 */
     int           count;          /* 0이 아니면 적어도 이만큼 더 온다 */
} XExposeEvent;

count가 핵심이다. 0이면 이 창에 대한 이번 묶음의 마지막 Expose다. 0이 아니면 적어도 그만큼(더 많을 수도 있음) 더 온다. 영역을 구분하지 않는 단순한 앱은 count가 0이 아닌 이벤트는 무시하고 0일 때만 전체를 다시 그리면 된다.

case Expose:
    if (ev.xexpose.count != 0) break;   /* 묶음의 마지막만 처리 */
    XClearWindow(dpy, win);
    XDrawString(dpy, win, gc, 20, 30, "hello", 5);
    break;
함정: 창을 매핑(XMapWindow)하자마자 그림을 그리면 아무것도 안 보일 수 있다. 창이 실제로 화면에 나타나기 전에 그린 것은 버려지기 때문이다. 그리기는 반드시 첫 Expose를 받은 뒤에, 그리고 매 Expose마다 한다.

GraphicsExpose와 NoExpose 이벤트

XCopyArea나 XCopyPlane으로 복사할 때, 원본 영역이 가려져 있거나 범위를 벗어나 대상의 일부를 계산할 수 없으면 서버가 GraphicsExpose를 보낸다. "그 부분은 복사 못 했으니 네가 그려라"라는 뜻이다. 한 그래픽 요청이 만든 영역은 연속해서 보고된다. 복사가 모두 성공해서 GraphicsExpose가 하나도 없으면 대신 NoExpose 하나를 보낸다. 그래서 스크롤처럼 복사 결과를 기다려야 하는 코드는 GraphicsExpose(count=0) 또는 NoExpose 중 하나가 올 때까지 기다리면 된다.

받으려면 GC의 graphics-exposures 속성이 True여야 한다(XCreateGC 때 지정하거나 XSetGraphicsExposures로). 이것은 마스크가 아니라 GC 속성으로 제어된다는 점이 다른 이벤트와 다르다.

typedef struct {
     int            type;           /* GraphicsExpose */
     unsigned long  serial;
     Bool           send_event;
     Display        *display;
     Drawable       drawable;
     int            x, y;
     int            width, height;
     int            count;          /* 0이 아니면 적어도 이만큼 더 온다 */
     int            major_code;     /* 코어에서는 CopyArea 또는 CopyPlane */
     int            minor_code;     /* 코어에서는 정의 안 됨 */
} XGraphicsExposeEvent;

typedef struct {
     int           type;         /* NoExpose */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Drawable      drawable;
     int           major_code;
     int           minor_code;
} XNoExposeEvent;
  • drawable: 복사의 대상 drawable. 창이 아니라 픽스맵일 수도 있어서 window가 아니라 drawable이다.
  • major_code: X_CopyArea 또는 X_CopyPlane(<X11/Xproto.h>). 어느 함수가 원인인지 알려 준다.
  • minor_code: 코어 프로토콜에서는 0. 확장이 쓸 수 있다.
  • x, y, width, height, count: Expose와 같은 뜻(좌표는 drawable 기준).
스크롤에 XCopyArea를 쓰지 않는 앱이라면 GC의 graphics-exposures를 False로 꺼 두는 것이 좋다. 안 그러면 픽스맵→창 복사를 할 때마다 NoExpose가 큐에 쌓인다.

10.10 창 상태 변화 이벤트

이 이벤트들은 창에 "이미 일어난" 변화를 알려 준다. 대부분 두 가지 방법으로 받는다. 그 창 자신에 StructureNotifyMask를 걸거나, 부모 창에 SubstructureNotifyMask를 걸어 모든 자식의 변화를 받는다. 그래서 구조체에 창이 두 개 있다. event는 이벤트를 받은 창(자기 자신 또는 부모)이고, window는 실제로 변한 창이다. 공용체 공통 부분의 다섯 번째 멤버는 event다(툴킷이 "받은 창" 기준으로 처리를 찾게 하려는 배치).

CirculateNotify

XCirculateSubwindows, XCirculateSubwindowsUp, XCirculateSubwindowsDown 때문에 창이 실제로 쌓임 순서(stacking order)를 바꿨을 때 생긴다.

typedef struct {
     int type;               /* CirculateNotify */
     unsigned long serial;
     Bool send_event;
     Display *display;
     Window event;
     Window window;
     int place;              /* PlaceOnTop, PlaceOnBottom */
} XCirculateEvent;

place는 바뀐 뒤의 위치다. PlaceOnTop이면 형제 중 맨 위, PlaceOnBottom이면 맨 아래.

ConfigureNotify

창의 크기·위치·테두리·쌓임 순서가 실제로 바뀌었을 때 생긴다. 원인이 되는 함수: XConfigureWindow, XLowerWindow, XRaiseWindow, XRestackWindows, XMoveWindow, XResizeWindow, XMoveResizeWindow, XMapRaised, XSetWindowBorderWidth. 일반 앱이 가장 자주 쓰는 구조 이벤트다. 사용자가 창 크기를 바꾸면 이 이벤트로 새 크기를 알게 된다.

typedef struct {
     int           type;       /* ConfigureNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;
     int           x, y;
     int           width, height;
     int           border_width;
     Window        above;
     Bool          override_redirect;
} XConfigureEvent;
  • x, y: 부모 창 기준, 테두리 바깥 왼쪽 위 모서리.
  • width, height: 테두리를 뺀 안쪽 크기.
  • border_width: 테두리 폭(픽셀).
  • above: 바로 아래 형제. None이면 이 창이 형제 중 맨 아래, 형제 창이면 이 창은 그 형제 바로 위에 있다.
  • override_redirect: 창의 override-redirect 속성. 창 관리자는 이것이 True인 창(팝업 메뉴 등)을 보통 무시해야 한다.
XSelectInput(dpy, win, ExposureMask | StructureNotifyMask | KeyPressMask);
...
case ConfigureNotify:
    if (ev.xconfigure.width != cur_w || ev.xconfigure.height != cur_h) {
        cur_w = ev.xconfigure.width;
        cur_h = ev.xconfigure.height;
        relayout();          /* 다시 그리기는 뒤따르는 Expose에서 */
    }
    break;
함정: 창 관리자가 최상위 창을 자기 프레임 창 안으로 리페어런트(reparent)하는 경우가 많다. 그러면 ConfigureNotify의 x, y는 루트가 아닌 프레임 기준이라 화면 위치로 쓸 수 없다. 화면 좌표가 필요하면 XTranslateCoordinates로 변환한다. 다만 send_event가 True인 합성 ConfigureNotify(창 관리자가 ICCCM 규약에 따라 보내는 것)에는 루트 기준 좌표가 들어 있다.

CreateNotify

XCreateWindow나 XCreateSimpleWindow로 창이 만들어지면 생긴다. 부모 창에 SubstructureNotifyMask를 걸어야만 받는다.

typedef struct {
     int           type;               /* CreateNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        parent;             /* 만들어진 창의 부모 */
     Window        window;             /* 만들어진 창 */
     int           x, y;               /* 부모 기준 바깥 왼쪽 위 */
     int           width, height;      /* 안쪽 크기, 항상 0이 아님 */
     int           border_width;
     Bool          override_redirect;
} XCreateWindowEvent;

DestroyNotify

XDestroyWindow나 XDestroySubwindows로 창이 없어지면 생긴다. 어떤 창이든 그 자손들의 DestroyNotify가 그 창 자신보다 먼저 생긴다(안쪽부터 바깥으로). 형제끼리나 다른 하위 트리 사이의 순서는 정해져 있지 않다.

typedef struct {
     int           type;       /* DestroyNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;     /* 없어진 창 */
} XDestroyWindowEvent;
이 이벤트를 받았을 때 window는 이미 없다. 그 ID로 Xlib 함수를 부르면 BadWindow 오류가 난다. 자기 자료 구조에서 지우는 데만 쓴다.

GravityNotify

부모의 크기가 바뀌어(XConfigureWindow, XMoveResizeWindow, XResizeWindow) 자식 창이 win_gravity에 따라 실제로 움직였을 때 생긴다.

typedef struct {
     int           type;       /* GravityNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;     /* 움직인 자식 창 */
     int           x, y;       /* 부모 기준 새 바깥 왼쪽 위 */
} XGravityEvent;

MapNotify

창이 매핑 안 됨 → 매핑됨으로 바뀌면 생긴다. 원인: XMapWindow, XMapRaised, XMapSubwindows, XReparentWindow, 또는 save-set 처리.

typedef struct {
     int           type;                  /* MapNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;
     Bool          override_redirect;
} XMapEvent;

창 관리자는 override_redirect가 True면 보통 무시한다. 이런 이벤트는 대개 구조 제어를 우회하는 팝업에서 생기기 때문이다.

"매핑됨"과 "보임"은 다르다. MapNotify는 매핑 요청이 끝났다는 뜻일 뿐, 그 창이 화면에 보인다는 보장은 아니다(부모가 언매핑 상태일 수 있다). 그리기 시점은 Expose로 판단한다.

MappingNotify

키보드·포인터 매핑이 바뀌면 모든 클라이언트에게 간다. 원하지 않는다고 표시하는 방법이 없다. 원인: XSetModifierMapping(어떤 키코드를 모디파이어로 쓸지), XChangeKeyboardMapping(키보드 매핑), XSetPointerMapping(버튼 매핑)이 성공했을 때.

typedef struct {
     int           type;           /* MappingNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;         /* 쓰이지 않음 */
     int           request;        /* MappingModifier, MappingKeyboard, MappingPointer */
     int           first_keycode;  /* 바뀐 첫 키코드 */
     int           count;          /* 바뀐 키코드 개수 */
} XMappingEvent;

first_keycode와 count는 request가 MappingKeyboard일 때만 의미가 있다. 클라이언트가 가진 키보드 정보를 갱신하려면 XRefreshKeyboardMapping을 부른다.

case MappingNotify:
    XRefreshKeyboardMapping(&ev.xmapping);   /* 키 변환 캐시 갱신 */
    break;
이 처리를 빼먹으면 사용자가 키 배치를 바꾼 뒤에도 앱은 옛 배치로 글자를 해석한다. 이벤트 루프에 이 세 줄은 거의 항상 넣는다.

ReparentNotify

XReparentWindow로 창의 부모가 실제로 바뀌면 생긴다. 창 자신에 StructureNotifyMask, 또는 옛 부모나 새 부모에 SubstructureNotifyMask를 걸어 받는다.

typedef struct {
     int           type;       /* ReparentNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;     /* 부모가 바뀐 창 */
     Window        parent;     /* 새 부모 */
     int           x, y;       /* 새 부모 기준 바깥 왼쪽 위 */
     Bool          override_redirect;
} XReparentEvent;

일반 앱은 창 관리자가 자기 최상위 창을 프레임에 넣을 때 이 이벤트를 받는다.

UnmapNotify

창이 매핑됨 → 매핑 안 됨으로 바뀌면 생긴다.

typedef struct {
     int           type;       /* UnmapNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        event;
     Window        window;     /* 언매핑된 창 */
     Bool          from_configure;
} XUnmapEvent;

from_configure는 창의 win_gravity가 UnmapGravity여서 부모 크기 변경 때문에 언매핑되었으면 True다.

VisibilityNotify

창이 얼마나 보이는지가 바뀌면 생긴다. "보인다"는 화면을 보는 사람이 실제로 볼 수 있다는 뜻이다. InputOnly 창에는 생기지 않는다. 계층 변화로 생긴 것은 그 계층 이벤트(Unmap/Map/Configure/Gravity/Circulate) 뒤에 오고, 한 창에 대해서는 Expose보다 먼저 온다(모든 창의 Visibility가 모든 창의 Expose보다 먼저라는 보장은 없다). FocusOut, Enter/Leave와의 순서는 정해져 있지 않다. VisibilityChangeMask로 받는다.

typedef struct {
     int           type;       /* VisibilityNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;
     int           state;      /* VisibilityUnobscured, VisibilityPartiallyObscured,
                                  VisibilityFullyObscured */
} XVisibilityEvent;

판단할 때 그 창의 자식 창들은 무시한다(자기 자식에 가려진 것은 가려진 것으로 치지 않는다).

  • 부분/완전히 가려짐 또는 보이지 않음 → 보이고 전혀 안 가려짐: VisibilityUnobscured
  • 전혀 안 가려짐 또는 보이지 않음 → 보이고 부분적으로 가려짐: VisibilityPartiallyObscured
  • 전혀 안 가려짐, 부분적으로 가려짐 또는 보이지 않음 → 보이지만 완전히 가려짐: VisibilityFullyObscured

쓸모: 애니메이션이나 게임에서 창이 완전히 가려졌으면(VisibilityFullyObscured) 그리기를 멈춰 CPU를 아낀다.

10.11 구조 제어 이벤트

이 이벤트들은 창 관리자(window manager)를 위한 것이다. 부모 창(보통 루트 창)에 SubstructureRedirectMask를 걸면, 다른 클라이언트가 그 자식 창을 매핑·이동·크기 변경·재배치하려 할 때 서버가 그 요청을 실행하지 않고 대신 요청 내용을 이벤트로 보내 준다. 창 관리자는 그것을 보고 원하는 대로(프레임을 씌우고 위치를 정하는 등) 처리한다. 이 마스크는 한 창에 한 클라이언트만 걸 수 있다. 그래서 한 화면에 창 관리자는 하나만 돌 수 있다. override-redirect 속성이 True인 창(팝업 메뉴, 툴팁)은 가로채이지 않는다.

CirculateRequest

다른 클라이언트가 XCirculateSubwindows, XCirculateSubwindowsUp, XCirculateSubwindowsDown을 불러 자식이 실제로 재배치되어야 할 때 생긴다. 예를 들어 어떤 앱이 XCirculateSubwindowsUp으로 자식을 맨 위로 올리려 해도, SubstructureRedirectMask를 건 클라이언트에게 CirculateRequest가 가고 실제로는 올라가지 않는다.

typedef struct {
     int           type;       /* CirculateRequest */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        parent;
     Window        window;     /* 재배치될 자식 */
     int place;                /* PlaceOnTop, PlaceOnBottom: 원하는 새 위치 */
} XCirculateRequestEvent;

ConfigureRequest

다른 클라이언트가 자식 창에 ConfigureWindow 프로토콜 요청을 보내면 생긴다. 원인 함수: XConfigureWindow, XLowerWindow, XRaiseWindow, XMapRaised, XMoveResizeWindow, XMoveWindow, XResizeWindow, XRestackWindows, XSetWindowBorderWidth. 창의 override-redirect가 False면 서버는 요청을 실행하지 않고 이 이벤트만 보낸다.

typedef struct {
     int           type;         /* ConfigureRequest */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        parent;
     Window        window;
     int           x, y;
     int           width, height;
     int           border_width;
     Window        above;
     int           detail;       /* Above, Below, TopIf, BottomIf, Opposite */
     unsigned long value_mask;
} XConfigureRequestEvent;

value_mask는 요청에 어떤 항목이 들어 있었는지(CWX, CWWidth 등)를 알려 준다. 들어 있던 값은 요청 그대로, 나머지는 창의 현재 값으로 채워진다. 단 above(형제)와 detail(stack-mode)은 요청에 없으면 각각 None, Above로 보고된다.

MapRequest

다른 클라이언트가 override-redirect가 False인 언매핑 창에 XMapWindow, XMapRaised, XMapSubwindows를 부르면 생긴다. 창은 매핑되지 않고 이 이벤트만 간다. 창 관리자는 이것으로 새 창의 배치를 통제한다.

typedef struct {
     int           type;       /* MapRequest */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        parent;
     Window        window;     /* 매핑하려는 창 */
} XMapRequestEvent;

아주 작은 창 관리자의 핵심 부분은 이런 모양이다.

XSelectInput(dpy, DefaultRootWindow(dpy),
             SubstructureRedirectMask | SubstructureNotifyMask);
for (;;) {
    XEvent ev;
    XNextEvent(dpy, &ev);
    if (ev.type == MapRequest) {
        /* 원하면 여기서 위치를 정하거나 프레임에 넣는다 */
        XMapWindow(dpy, ev.xmaprequest.window);   /* 대신 매핑해 준다 */
    } else if (ev.type == ConfigureRequest) {
        XConfigureRequestEvent *r = &ev.xconfigurerequest;
        XWindowChanges wc;
        wc.x = r->x; wc.y = r->y;
        wc.width = r->width; wc.height = r->height;
        wc.border_width = r->border_width;
        wc.sibling = r->above; wc.stack_mode = r->detail;
        XConfigureWindow(dpy, r->window, (unsigned int)r->value_mask, &wc);
    }
}
가로챈 클라이언트(창 관리자) 자신이 부르는 XMapWindow/XConfigureWindow는 다시 가로채이지 않는다(원문 표현으로 "다른 클라이언트가" 요청할 때만 Request 이벤트가 생긴다). 그래서 위처럼 받은 요청을 대신 실행할 수 있다. 다른 창 관리자가 이미 돌고 있으면 XSelectInput이 BadAccess 오류를 낸다.

ResizeRequest

다른 클라이언트가 XConfigureWindow, XResizeWindow, XMoveResizeWindow로 그 창의 크기를 바꾸려 하면 생긴다. 그 창에 ResizeRedirectMask를 걸어 받으며, 크기 변경 시도는 가로채인다.

typedef struct {
     int           type;        /* ResizeRequest */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;
     int           width, height;   /* 요청된 안쪽 크기(테두리 제외) */
} XResizeRequestEvent;

10.12 컬러맵 상태 변화 이벤트

창의 컬러맵이 바뀌거나 컬러맵이 설치/해제되면 ColormapNotify가 생긴다. 원인: XChangeWindowAttributes/XSetWindowColormap으로 창의 colormap 속성을 바꾸거나 XFreeColormap으로 컬러맵을 해제할 때, 그리고 XInstallColormap/XUninstallColormap. ColormapChangeMask로 받는다. 요즘의 트루컬러 화면에서는 거의 쓰이지 않는다.

typedef struct {
     int           type;       /* ColormapNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;
     Colormap      colormap;   /* 컬러맵 또는 None */
     Bool          new;
     int           state;      /* ColormapInstalled, ColormapUninstalled */
} XColormapEvent;
  • colormap: 창에 연결된 컬러맵. XFreeColormap으로 해제된 경우 None.
  • new: True면 창의 컬러맵이 바뀐 것, False면 설치/해제된 것.
  • state: 지금 설치되어 있는지(ColormapInstalled/ColormapUninstalled). 항상 채워진다.
C++ 컴파일러로 빌드하면 멤버 이름 new가 예약어와 충돌한다. 그래서 Xlib 헤더는 C++에서 이 멤버를 c_new로 바꿔 선언한다.

10.13 클라이언트 간 통신 이벤트

ClientMessage

서버가 스스로 만드는 일은 없다. 어떤 클라이언트가 XSendEvent를 부를 때만 생긴다. 내용은 서버가 해석하지 않고 그대로 전달하므로, 프로그램끼리 자유롭게 짧은 메시지를 주고받는 데 쓴다. 대표적인 예가 창 관리자가 보내는 WM_PROTOCOLS/WM_DELETE_WINDOW("닫기 버튼이 눌렸다") 메시지다.

typedef struct {
     int           type;           /* ClientMessage */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;
     Atom          message_type;
     int           format;
     union {
         char  b[20];
         short s[10];
         long  l[5];
     } data;
} XClientMessageEvent;
  • message_type: 데이터를 어떻게 해석할지 나타내는 아톰(받는 쪽과 약속한 이름).
  • format: 8, 16, 32. 데이터를 바이트(b[20]), short(s[10]), long(l[5])의 목록으로 볼지 정한다. 메시지 종류에 따라 일부만 쓸 수 있다.
  • 서버는 window, message_type, data를 전혀 해석하지 않는다.
/* 창 닫기 버튼 처리 */
Atom wm_protocols = XInternAtom(dpy, "WM_PROTOCOLS", False);
Atom wm_delete    = XInternAtom(dpy, "WM_DELETE_WINDOW", False);
XSetWMProtocols(dpy, win, &wm_delete, 1);
...
case ClientMessage:
    if (ev.xclient.message_type == wm_protocols &&
        (Atom)ev.xclient.data.l[0] == wm_delete)
        running = 0;
    break;
format 32라도 data.l은 C의 long이다. 64비트 시스템에서 long은 8바이트지만 전송되는 값은 32비트씩 5개다. 그래서 항상 l[0]~l[4]로 읽고 쓰며, 다른 타입 배열로 memcpy하지 않는다.

PropertyNotify

창의 프로퍼티가 바뀌면 생긴다. PropertyChangeMask로 받는다.

typedef struct {
     int           type;       /* PropertyNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;
     Atom atom;                /* 바뀐 프로퍼티 */
     Time time;                /* 바뀐 서버 시각 */
     int state;                /* PropertyNewValue 또는 PropertyDelete */
} XPropertyEvent;

state가 PropertyNewValue가 되는 경우: XChangeProperty나 XRotateWindowProperties로 값을 바꿨을 때(길이 0 데이터를 덧붙여도, 같은 값으로 덮어써도 생긴다). PropertyDelete가 되는 경우: XDeleteProperty로 지웠거나, delete 인자를 True로 준 XGetWindowProperty로 읽었을 때.

요령: 셀렉션 함수 등에 넣을 "현재 서버 시각"이 필요하면, 자기 창에 길이 0 데이터를 PropModeAppend로 XChangeProperty하고 돌아오는 PropertyNotify의 time을 쓴다. 위 규칙(길이 0이어도 이벤트가 생김) 덕분에 가능한 방법이다.

SelectionClear

셀렉션(복사·붙여넣기의 바탕 구조)의 소유권을 잃는 클라이언트에게 간다. 다른 클라이언트가 XSetSelectionOwner로 소유권을 가져갈 때 생긴다. 받으면 선택 표시(하이라이트)를 지우면 된다.

typedef struct {
     int           type;       /* SelectionClear */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        window;     /* 잃는 쪽이 XSetSelectionOwner에 줬던 창 */
     Atom          selection;  /* 셀렉션 아톰 */
     Time          time;       /* 셀렉션의 마지막 변경 시각 */
} XSelectionClearEvent;

SelectionRequest

셀렉션 소유자에게 간다. 다른 클라이언트가 그 셀렉션에 대해 XConvertSelection을 부르면(즉 붙여넣기를 하면) 생긴다.

typedef struct {
     int           type;       /* SelectionRequest */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        owner;      /* 소유자가 XSetSelectionOwner에 줬던 창 */
     Window        requestor;  /* 요청한 창 */
     Atom          selection;  /* 예: PRIMARY */
     Atom          target;     /* 원하는 데이터 형식 */
     Atom          property;   /* 결과를 넣을 프로퍼티 또는 None */
     Time          time;       /* ConvertSelection 요청의 시각 또는 CurrentTime */
} XSelectionRequestEvent;

소유자는 target 형식으로 데이터를 변환해 요청자 창의 프로퍼티에 넣고, SelectionNotify 이벤트를 요청자에게 보내야 한다. 셀렉션 사용법의 완전한 규칙은 X 컨소시엄 표준 ICCCM(Inter-Client Communication Conventions Manual)에 있다.

SelectionNotify

셀렉션에 소유자가 없으면 ConvertSelection 요청에 대한 응답으로 서버가 직접 만든다. 소유자가 있으면 소유자가 XSendEvent로 만들어 보내야 한다. 변환해서 프로퍼티에 저장했을 때, 또는 변환할 수 없을 때(property를 None으로) 보낸다. 요청에서 property가 None이었다면 소유자가 프로퍼티 이름을 골라 요청자 창에 저장하고 그 실제 이름을 담아 보낸다.

typedef struct {
     int           type;       /* SelectionNotify */
     unsigned long serial;
     Bool          send_event;
     Display       *display;
     Window        requestor;
     Atom          selection;  /* 예: PRIMARY */
     Atom          target;     /* 변환된 형식, 예: PIXMAP */
     Atom          property;   /* 결과가 저장된 프로퍼티, 실패하면 None */
     Time          time;       /* 변환 시각 또는 CurrentTime */
} XSelectionEvent;

소유자 쪽에서 요청에 응답하는 예(11.6절의 XSendEvent 참고):

case SelectionRequest: {
    XSelectionRequestEvent *rq = &ev.xselectionrequest;
    XEvent reply;
    memset(&reply, 0, sizeof reply);
    reply.xselection.type      = SelectionNotify;
    reply.xselection.requestor = rq->requestor;
    reply.xselection.selection = rq->selection;
    reply.xselection.target    = rq->target;
    reply.xselection.time      = rq->time;
    if (rq->target == XA_STRING && rq->property != None) {
        XChangeProperty(dpy, rq->requestor, rq->property, XA_STRING, 8,
                        PropModeReplace, (unsigned char *)text, strlen(text));
        reply.xselection.property = rq->property;
    } else {
        reply.xselection.property = None;        /* 변환 실패 */
    }
    XSendEvent(dpy, rq->requestor, False, 0, &reply);
    break;
}

(XA_STRING은 <X11/Xatom.h>에 있다. 실제 프로그램은 TARGETS, UTF8_STRING 등도 처리해야 한다.)
